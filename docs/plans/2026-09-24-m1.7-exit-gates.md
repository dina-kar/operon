**Goal:** Prove milestone M1 and close it. Ship:
- the conformance runner and the four framework suites of the M1 gate (LangChain and LlamaIndex vector stores, Elasticsearch and Qdrant backends), plus the `qdrant-client` Python client suite, run unmodified against Operon's gateways, each measured against a real Elasticsearch or Qdrant oracle;
- the ADBC Flight SQL driver gate (D49): the Go driver `github.com/apache/arrow-adbc/go/adbc/driver/flightsql` through ADBC's own `validation` suites, and the Python driver `adbc-driver-flightsql` through its DBAPI, both against `operon dev`'s Flight SQL listener, including `DoPut` bulk ingest (`adbc_ingest`) into a collection and a stream; and Spice's Flight SQL connector (D56): a pinned Spice runtime whose spicepod reads an Operon collection through `from: flightsql:…`, checked with plain SQL;
- the BEIR harness: nDCG@10 per dataset within 1 point of Elasticsearch BM25;
- the recall harness: Recall@10 within 1% of Qdrant at equal hot-tier latency, unfiltered and filtered;
- the hot on/off differential harness at scale, and the CI mode that disables the hot tier at random per request;
- object-store request counts per query in every benchmark result, with a regression check;
- the CI tiers (every PR, nightly, pre-release) and the M1 exit report.

**Architecture:**
- `operon-store::CountingStore` wraps the server's one object store and counts requests per operation and per path class, as S3 would bill them. The `operon` binary exposes the counters and per-gateway request counters at `GET /v1/admin/metrics`, and gains `--hot-chaos <p>`, a tower layer that adds `Operon-Hot: off` to a seeded random fraction of incoming requests.
- `bench/` is one Python project (uv, Python 3.12), package `operon_bench`: server and oracle lifecycle, datasets, result files, metrics and gate rules. It holds three harnesses: `bench/beir/`, `bench/recall/` and `bench/differential/`. Results are JSON files under `bench/results/`, committed only from the reference machine.
- `conformance/` is a second Python project that depends on `operon_bench`. `suites.toml` pins each upstream suite (repository, tag, commit, install command, test command, environment). `run.py` clones the suite at its commit into `target/conformance/`, installs it with the suite's own lock file, runs its own pytest command with only the environment pointing at Operon (or at the oracle), and writes a report with one outcome per test. `expected/<suite>.json` is the committed outcome of the same run against the real oracle; the gate compares the two. The ADBC driver suites (Task 4) run through the same runner: `conformance/adbc/go/` is a Go module that runs ADBC's upstream `validation` suites with an Operon quirks file, and `conformance/adbc/python/` is a pytest file over the published Python driver; they have no oracle (Ruling 16). The Spice suite (Task 4, Ruling 17) is a pytest file of ours, `conformance/spice/test_spice_flightsql.py`, that starts a pinned Spice container against `operon dev`; it has no oracle either.
- Elasticsearch and Qdrant run only as external oracles, in containers (podman or docker, `--network host`), pinned by digest (overview R14). No Elastic code, spec or test resource enters the repository. The ADBC drivers and the `validation` package are Apache-2.0 test dependencies, fetched at pinned versions and never vendored.
- CI tiers (Task 8): **smoke** on every PR (`ci.yml` jobs `python` and `gates-smoke`: debug build, minutes); **nightly** (`gates.yml`: release build, all eight suites plain and under hot chaos, the BEIR nightly subset, recall on `glove-100-angular`, the differential at medium scale, the cost check); **full** (`gates.yml` by `workflow_dispatch`, and by hand on the reference machine before a release and for the exit report: everything).

## Global Constraints

Same as the M1 overview §8, plus:
- **Unmodified means unmodified** (Ruling 1). An upstream framework suite runs from its release's files at a pinned commit, installed from its own lock file (or, where upstream has none, a lock we commit under `conformance/locks/`), with its own test command. Operon may only change the environment (variables, a running server, the ports it listens on) and append `--junitxml <path> -rA -p no:cacheprovider` (plus `-p no:xdist` for `langchain-qdrant`, Ruling 4). No conftest, plugin, patch, monkeypatch, `-k` or `--deselect` of ours in a gated run. Exclusions are by stated feature rule only (Ruling 3): excluded tests still run and are reported. The ADBC Go gate runs ADBC's `validation` package unmodified at its pinned version; the one file of ours it needs, the Operon `DriverQuirks`, only declares which features Operon serves, each with a stated reason (Ruling 16).
- **Every gate is non-vacuous.** A gate run fails when: a server-backed suite produced no gateway request; a harness ran zero queries; the hot-on side of a differential never used a hot structure; an oracle run is missing (the ADBC and Spice suites have no oracle, Rulings 16 and 17); the ADBC gate proved no `DoPut` ingest; or Spice's queries produced no Flight SQL request to Operon. A skipped or empty run is never a pass.
- **Measure the oracle, do not quote it.** Every reference number and every expected test outcome comes from a run of the same harness against the real server, recorded with its image digest. Published numbers (BEIR paper, ann-benchmarks site) are only sanity checks.
- **Scratch space:** datasets live in `target/bench-data/`, upstream clones and their environments in `target/conformance/`, run outputs in `target/gates/`. Never `/tmp`: it is a small tmpfs on the reference machine.
- **Python:** Python 3.12, uv only (`uv sync --locked`, `uv run`). `bench/uv.lock` and `conformance/uv.lock` are committed. Python code passes `ruff check` and `ruff format --check` (ruff 0.16.8) and `pytest` in CI.
- **Results:** a committed result file is written only by the full tier on the reference machine and committed by a human in a PR; CI never commits.
- Commit areas used: `store`, `operon`, `bench`, `conformance`, `ci`, `docs`.

## Review Focus

1. **A gate that passes because nothing ran.** The llama-index suites skip every test when no server answers; ADBC's `validation` suites skip every test a quirk declares unsupported, so an over-cautious quirks file passes vacuously; a hot-off switch that switches nothing makes the differential trivially identical; a harness with zero queries passes every "all queries" rule; Spice could answer from its accelerated copy without reaching Operon. Tests: Task 3 `a_forbidden_skip_message_fails_the_gate`, `zero_gateway_requests_fail_the_gate`, `a_new_or_missing_test_is_drift`; Task 4 `a_quirk_skip_without_a_listed_reason_is_refused`, `bulk_ingest_cannot_be_quirked_away`, `spice_without_a_flight_sql_request_fails_the_gate`; Task 7 `a_hot_used_header_on_a_hot_off_response_fails_the_run` and Semantics 6; Task 6 Semantics 4 (≥ 99% `hnsw`); Task 1 `hot_chaos_injects_the_header_at_the_configured_rate`.
2. **Local-mode tests counted as server passes.** Qdrant `:memory:` and `path=` variants pass regardless of Operon (the LlamaIndex hybrid tests are all `:memory:`), and an exclusion rule, should one be needed, must match only its own parameter (test ids contain vector names such as `my-sparse-vector`). Tests: Task 3 `server_and_local_tests_are_classified_by_params`, `a_dense_id_containing_sparse_in_a_vector_name_is_not_excluded`, `node_ids_are_reconstructed_from_junit`.
3. **Latency comparisons skewed by the machine rather than the engine**: a hybrid CPU (performance vs efficiency cores), rootless container networking, frequency drift, the two engines measured minutes apart. Tests and rules: Task 2 Semantics 2–3 (`--network host`, CPU sets) and `an_image_runs_by_digest`; Task 6 `a_noisy_qdrant_rerun_makes_the_run_invalid`, `the_gate_fails_when_operon_cannot_reach_qdrants_latency`, `too_few_points_in_range_make_the_run_invalid`.
4. **Ties, float noise and identical ids in the metrics.** Tied neighbours at the k-th distance, scores that differ in the last bit, arguana queries whose own text is in the corpus, queries with no hits. Tests: Task 2 `recall_counts_ties_at_the_kth_distance`, `int_and_float_differ`; Task 7 `volatile_fields_are_ignored_and_nothing_else`, `a_non_exact_score_is_reported`; Task 5 `identical_ids_are_ignored`, `a_query_without_hits_drops_out_of_the_mean`, `ndcg_matches_a_hand_computed_value`.
5. **Hot structures older than the data.** After upserts, deletes and partial updates, the HNSW artifact and the pinned splits still reflect the previous manifest while the tail and delete bitmaps move on; identity must hold in that window, not only after a rebuild. Tests: Task 7 phases `tail`, `applied`, `rebuilt` and `the_oracle_model_applies_mutations`; Task 5 Semantics 6 (nDCG identical across cold, warm and hot phases).

`ServerConfig` gains `pub hot_chaos: Option<HotChaos>` (default `None`). `operon dev` gains hidden flags `--hot-chaos <p>` and `--hot-chaos-seed <u64>` (default seed 0); `operon standalone` does not get them. (`--hot-pin-all` is M1.3's, A13.)

**Semantics:**
1. **Counting rules (they model what S3 bills, whatever the backend):**
   - `get_opts` with `options.head == true` → `head += 1`; otherwise `get += 1` and `get_bytes +=` the length of the returned range (for a whole-object GET, the object size from `GetResult.meta.size`, counted when the call returns, not when the stream is drained).
   - `get_ranges` is **not** overridden: the trait's default coalesces the ranges and calls `self.get_opts` once per coalesced range, which is how the S3 backend issues them, so each coalesced range counts one GET even over `file://`.
   - `put_opts` → `put += 1`, `put_bytes += payload.content_length()`.
   - `put_multipart_opts` → `put += 1` at initiation; the returned upload is wrapped so that each `put_part` adds `put += 1` and its bytes, and `complete` adds `put += 1`; `abort` adds `delete += 1`.
   - `list` and `list_with_offset` → `list += 1` when the stream is created, plus `list += 1` for every further 1000 items yielded (S3 pages hold 1000 keys); `list_with_delimiter` → `list += 1`.
   - `delete_stream` → `delete += 1` per path yielded by the input stream.
   - `copy_opts` → `copy += 1`; `rename_opts` is not overridden (default = copy + delete).
   - Every request is counted whether it succeeds or fails, under the `PathClass` of its path (for `copy`, of the destination).
2. **`PathClass::of(path)`**, on the path relative to the store root (after any bucket prefix), first match wins: `meta/` → `Meta`; `wal/` → `Wal`; `ns/*/streams/` → `Segment`; `ns/*/links/` → `Link`; `ns/*/collections/*/lance/` → `Lance`; `ns/*/collections/*/text/splits/` → `Split`; `ns/*/collections/*/text/deletes/` → `SplitDeletes`; `ns/*/collections/*/manifests/` → `Manifest`; `ns/*/collections/*/hot/` → `Hot`; `ns/*/pk/` → `Pk`; anything else → `Other` (`*` is exactly one path segment).
3. **Server wiring.** `Server::start` builds the store as today, then replaces it with `Store::new(Arc::new(CountingStore::new(store.inner().clone(), counters.clone())))` before anything else uses it, so the metastore, the log, the cache, Lance, SlateDB and the hot tier all see the counting wrapper (Task 0 A10). Counting is always on (a handful of relaxed atomic adds per request).
4. **Gateway request counters.** Every listener's service stack gets a counting layer (outermost, after the chaos layer) that increments `requests` for its `Surface` and, when the response carries `Operon-Hot-Used` (gRPC response metadata `operon-hot-used`) with a value other than `none`, `hot_used_responses`; `hot_off_requests` counts requests that carry `Operon-Hot: off` after the chaos layer ran.
5. **Hot chaos.** For request number `n` on a surface (a per-surface `AtomicU64` starting at 0), draw `u = ChaCha8Rng::seed_from_u64(seed ^ ((surface as u64) << 56) ^ n).random::<f64>()` (`surface as u64` = the variant's index in declaration order); if `u < probability` and the request has no `Operon-Hot` header, insert `Operon-Hot: off` (gRPC: metadata `operon-hot: off`) and increment `chaos_injected`. Requests with an explicit `Operon-Hot` header are left alone. The chaos layer wraps each listener outside its `HotLayer` (M1.2), so `HotLayer` sees the injected header. The layer applies to every surface that serves reads (native, ES, Qdrant REST, Qdrant gRPC, Flight SQL (metadata `operon-hot`), MCP). `--hot-chaos` with `--hot=off` is rejected at startup (`ServerError::Config("--hot-chaos needs the hot tier on")`; add the variant if Task 0 finds none).
6. **Metrics route.** `GET /v1/admin/metrics` on the native listener returns 200:
   ```json
   {"store": {"total": RequestCounts, "by_class": {"<path_class>": RequestCounts, …}},
    "gateways": {"<surface>": SurfaceCounts, …},
    "hot_chaos": {"probability": f64, "seed": u64} | null}
   ```
   Classes and surfaces with all-zero counts are omitted. The route is served in `operon dev` and `operon standalone` (no authentication in M1, overview §6.9).

2. **Oracles.** `bench/oracles.toml` pins each image by tag **and** digest (`image@sha256:…` is what runs); the digests are recorded by the first `operon-bench fetch --oracles --record-hashes` and committed. Containers are named `operon-oracle-<es|qdrant>-<run_id>` and removed on exit, including on `KeyboardInterrupt`.
3. **CPU sets.** `default_cpusets()`: with ≥ 8 logical CPUs, the server (Operon or oracle, via `taskset` or `--cpuset-cpus`) gets the first 4 CPUs and the client the next 2; otherwise the server gets the first half and the client the rest. 5. **Datasets.** `bench/datasets.toml` has one table per dataset: `name`, `files` (url, size in bytes, sha256, license), `kind` (`beir` | `ann-hdf5` | `vdbbench-parquet`), and the dataset facts the harness asserts after loading (document/query/dimension counts). `fetch` downloads with HTTP range resume into `target/bench-data/<name>/`, checks the size and the sha256, and extracts zips. 6. **Result files.** `write_result` writes `<out_dir>/<gate>/<dataset>/<run_id>-<machine name>.json`, pretty-printed (2 spaces, sorted keys, trailing newline), validated against `result.schema.json`. The envelope:
   ```json
   {"format": "operon-bench-result", "version": 1, "gate": "beir|recall|differential|conformance", "dataset": str,
    "run_id": str, "started_at": RFC3339, "finished_at": RFC3339,
    "operon": {"git_sha": str, "dirty": bool, "profile": "release|debug", "flags": [str]},
    "oracle": {"image": str, "digest": str, "version": str} | null,
    "machine": {…item 4…}, "params": {…}, "measurements": {…},
    "store_requests": {"<phase>": {"queries": int, "per_query": {"get": f, "head": f, "put": f, "list": f, "class_a": f, "class_b": f, "get_bytes": f}, "by_class": {"<class>": {…same…}}}},
    "gate_result": {"pass": bool, "rule": str, "violations": [str]}}
   ```
   `out_dir` is `target/gates/results` by default; `--commit-results` writes to `bench/results/` instead and is refused unless `operon.dirty` is false and `profile` is `release`.
7. **Object-store counts per query.** `StoreCounter.quiesce` samples the counters twice `window_s` apart and returns when no class other than `meta` and `wal` changed in the window; it raises `NotQuiescent` with the moving classes after `timeout_s`. Benchmarks call it before each measured phase and run the phase single-client and sequentially, so `measure(phase)` divided by the phase's query count is the per-query cost. A phase's counts include every class; the harness also records them `by_class`.
8. **Cost regressions.** `cost_regressions(new, baseline)` compares `store_requests.<phase>.per_query.class_b` and `.class_a` of a new result with the latest committed result of the same gate, dataset and machine, and reports a regression when `new > baseline × 1.10 + 0.05`. A baseline of 0 (hot phases) therefore tolerates no more than 0.05 requests per query. `operon-bench check-cost <result.json>…` exits 1 on any regression and prints each one; a missing baseline prints a notice and passes.
9. **Recall rule** (`recall_at_k`, the ann-benchmarks `knn` rule, so ties at the k-th distance do not penalise either engine): let `t` = `true_dists[k-1] + 1e-3` (distances in the dataset's metric: angular = 1 − cosine, Euclidean = L2); recall = |{i < k : found_dists[i] ≤ t}| / k, where `found_dists` are the **exact** distances of the returned ids, recomputed by the harness from the dataset vectors in float64. The ids in `true_ids` are used only when `true_dists` is absent (then recall = |found[:k] ∩ true_ids[:k]| / k).
10. **Latency matching.** `pareto_frontier` keeps the points not dominated (lower latency and higher recall); `recall_at_latency` interpolates linearly between the two frontier points that bracket the latency, returns the frontier's best recall at or below it when the latency is beyond the slowest point, and `None` when the latency is below the fastest point.
11. **Canonical JSON.** `canonical_json` sorts object keys recursively by code point, keeps array order, renders numbers with Python's shortest round-trip `repr` for floats and plain integers for ints (so `1.0` and `1` differ, as they do on the wire), renders strings with `ensure_ascii=False`, separators `(",", ":")`, and removes every object key whose dotted path (array indices dropped) is in `drop`.

**Semantics:**
1. **Clone and install.** `clone` fetches exactly `commit` (`git init`, `git fetch --depth 1 <repo> <commit>`, `git checkout FETCH_HEAD`; for `run-llama/llama_index` and `langchain-ai/langchain` a sparse checkout of `subdir` plus the repository root files) into `target/conformance/<suite>/src/` and refuses to continue if `git rev-parse HEAD` differs or a tracked file changed after install (`git diff --quiet HEAD` fails); untracked files (virtual environments, the copied lock) are allowed. Each suite's virtual environment lives inside its clone, created by its own install commands with `UV_PYTHON=3.12`. Clones and environments are reused across runs when the commit matches.
2. **Serial execution.** Every suite runs with one pytest process. `langchain-qdrant`'s `conftest.py::pytest_runtest_teardown` deletes every collection on every location after every test, so xdist workers sharing one server delete each other's data; this breaks against real Qdrant too, and upstream CI never noticed because it only runs `:memory:`. That is the only upstream flag we change (`-n auto` → `-p no:xdist`).
3. **Test identity and classes.** A test id is the junit `classname` (dots to `/`, `.py`) + `::` + `name`, exactly pytest's node id. Before the run, `collect_params` runs `pytest --collect-only -q -p conformance.collect_params` with the suite's own command arguments; the plugin (`collect_params.py`, used **only** in this collect-only pass) writes each item's `callspec.params` as `repr` strings to `target/conformance/<suite>/params.json`. A test is **server-backed** when a `server_params` regex matches one of its params or its function name is in `server_names`; otherwise it is `local` (Qdrant `:memory:` or `path=` mode, pure unit tests). A test is **excluded** when an `excluded_params` regex matches the repr of the named param or its function name contains an `excluded_names` substring. Excluded tests still run (nothing is deselected); their outcomes are reported and ignored by the gate.
4. **Targets.** `--target oracle` runs the suite against the real server: Elasticsearch `docker.io/library/elasticsearch:8.19.22` by digest with `discovery.type=single-node`, `xpack.security.enabled=false` and `xpack.license.self_generated.type=trial` (upstream CI's settings, so the licence-gated tests run), ML left enabled (so the "model not deployed" checks get 404 and skip); Qdrant `docker.io/qdrant/qdrant:v1.19.1` by digest. `--target operon` runs a fresh `operon dev` per suite (release binary unless `--debug`), with `--hot-chaos` when given.    - `rebuilt`: wait until `hot.vectors.source_version` and `hot.text.source_version` equal `manifest_version`; compare.
3. **The generator** (seeded `random.Random(seed)`, weights in parentheses; every query is valid for the collection):
   - ES `_search`, identical class (45%): `match` on `txt` with 1–4 terms drawn from the corpus vocabulary weighted by document frequency, or a BEIR test query (half each), random `operator`; `match_phrase` with a 2–3 word window of a random document; `multi_match` best_fields over `title`/`txt` with `tie_breaker` 0.5; `fuzzy` (fuzziness 1–2) on a vocabulary term; `prefix` and `wildcard` on `tag`; `query_string` with `AND`/`OR` of two terms; each optionally inside a `bool` with 0–2 filters from {`term tag`, `terms tags`, `range n`, `range ts`, `exists tags`, `term flag`} and 0–1 `must_not`; `size` 1–100, `from` 0–50; `sort` one of score, `n` asc, `ts` desc then `n` asc (Operon appends the PK tie-break itself, overview R10); `_source` all, none or `includes: ["title", "tag"]`; `track_total_hits` true (50%). Aggregations, highlighting and point in time are not sent to the ES gateway: they are Phase B there (D48, M1.5 "Moved to Phase B (D48)").
   - Native aggregations and highlighting, identical class (15%): native `query` requests with `limit: 0` and one aggregation in the search IR's aggregation JSON (overview §6.6; M1.2 Task 8): `terms tag` (size 10), `histogram n` (interval 1000), `date_histogram ts` (`fixed_interval` `30d`), `range f` (3 ranges), `stats n`, `avg/sum/min/max f`, `cardinality tags`, `percentiles f` ([50, 95, 99]), `terms tag` with a `top_hits` sub-aggregation (size 3, sorted by `n`), under a random text query or filter from the list above; and, in a quarter of them, `limit` 10 with `highlight` on `txt`.
   - ES `_count` and `_mget` of 1–20 random ids, identical class (5%).
   - Qdrant, identical class (15%): `POST /collections/diff-<dataset>/points/query` with `using: "vec"` (the ES `dense_vector` field is the Qdrant named vector `vec`), `params.exact = true`, a query vector = a random document's `vec` plus N(0, 0.05) noise, normalised, `limit` 1–50; `points/scroll` with `limit` 1–100, one page; `points/count` with `exact: true`. Qdrant requests carry no `filter`: Qdrant filters address `payload.<key>` (overview A3), and an index created through the ES gateway has no `payload` field, so every filter would match nothing; and `next_page_offset` is a string id here (BEIR ids are `PrimaryKey::Str`), which the Qdrant API does not accept as input (M1.4 Ruling 18), so scroll is not paged. Filtered and paged reads are covered on the ES and native surfaces.
   - Native, identical class (5%): a hybrid `query` with a text retriever (`match` on `txt`) and an **exact** vector retriever fused with `rrf` (k 60), a filter, `limit` 10.
   - Approximate class (15%): Qdrant `points/query` with default `params` (no filter, as above), and ES `knn` (`k` 10, `num_candidates` 100) with an optional filter.
   ES paging with `search_after` (2% of ES queries): `sort` `[n asc, ts asc]`, `size` 50, each next page from the last hit's `sort` values (no point in time: Phase B in M1.5, its Ruling 10), until a page is empty or 20 pages were read, on both sides; compare every page.
   The differential collection is created through the ES gateway, which has no sparse field type (M1.5 Ruling 13), so this harness sends no sparse query; sparse hot on/off identity is proven by M1.3 Task 12 (sparse vector `sp`, identical class) and M1.2 Task 15, and exercised at suite scale by the `langchain-qdrant` and `qdrant-client` sparse tests under `--hot-chaos` (Semantics 7).
4. **Identical class.** Each query is sent twice, once with `Operon-Hot: off` and once without, in an order chosen by the seed. The differential server runs with `--maintenance off` (Task 0 A14, M1.3 Task 8), so no split merge or Lance compaction can commit between the two requests of a pair (a merge reorders ties that M1.2 leaves in split order, for example `top_hits` hits equal on every sort key, M1.2 Task 8 rule 5); link apply, index builds and hot artifact commits still run and cannot change an identical-class result (M1.2 Task 15). Identity across maintenance commits is M1.3 Task 12's `maintained` phase, which pins both executions to one manifest. Reads are not pinned here because the Qdrant REST surface has no pinned-read form. The two HTTP statuses must be equal and `canonical_json(body, drop=VOLATILE[surface])` byte-equal. Scores are part of the body and compared exactly (overview R12). A mismatch is saved to `target/gates/<run_id>/diff/failures/<phase>-<query id>.json` with the request, both responses and both `Operon-Hot-Used` headers.
5. **Approximate class (overview R12's rule).** For each response (hot on and hot off separately): (a) every hit satisfies the query's filter, evaluated by the harness's own model of the collection (`oracle_model.py`: the documents as written, with the mutations applied); (b) every hit's score equals the exact score of its stored vector in the model (cosine similarity; ES `knn` reports `(1 + cos) / 2`) within `1e-4 × max(1, |exact|)`; (c) over all approximate queries of the phase, recall@10 against the model's exact top-10 (tie-tolerant rule, Task 2 Semantics 9) is computed per tier. The phase passes (c) iff each tier's recall is `≥ R_qdrant − 0.01`, where `R_qdrant` is the recall of the same queries against the Qdrant oracle loaded with the same vectors and payloads (`m` 16, `ef_construct` 128, default search parameters), measured by the harness at the end of the run (for `tail`, `applied` and `rebuilt`, the oracle is loaded with the mutated data).
6. **Non-vacuity.** Hot-off responses must all carry `Operon-Hot-Used: none` (anything else is a switch leak and fails the run). In phases `loaded` and `rebuilt`, hot-on responses must report `splits` for ≥ 90% of text queries and `hnsw` for ≥ 90% of approximate vector queries; otherwise the run fails ("the hot tier was not exercised").
7. **Random disabling in CI (§12 §2 item 5).** Besides this harness, the smoke and nightly tiers run the conformance suites with `operon dev --hot-chaos 0.5 --hot-chaos-seed <CI run number> --hot-pin-all` (A13: every collection is pinned when it is created), so every suite's own assertions run with the hot tier randomly disabled per request; the report records `gateways.*.chaos_injected`, which must be > 0.
8. **Result.** `measurements` records per phase and class: queries, mismatches, approximate recall per tier and Qdrant's, the hot-used fractions; `store_requests` per phase and tier. The gate passes iff there are 0 mismatches and every check in 5–6 holds in every phase.

**Produces:**

```rust
// operon-query/src/recall.rs (serde; field names are the JSON keys)
pub struct RecallRequest {
    pub vector: String,             // the dense vector field
    pub num: u32,                   // 25; 1..=100
    pub k: u32,                     // 10; 1..=1_000
    pub filter: Option<Query>,
    pub params: AnnParams,          // the ANN side; `exact` must be false
    pub seed: Option<u64>,          // None: a random seed, reported
    pub return_samples: bool,       // false
}
pub struct RecallResponse {
    pub vector: String, pub num: u32, pub k: u32, pub seed: u64, pub manifest_version: u64,
    pub queries_evaluated: u32,
    pub avg_recall: Option<f64>, pub min_recall: Option<f64>,   // None when no query was evaluated
    pub avg_ann_count: f64, pub avg_exact_count: f64,
    pub hot_used: BTreeSet<HotKind>,
    pub samples: Option<Vec<PrimaryKey>>,                        // with return_samples
}
impl CollectionService { pub async fn recall(&self, ns: &str, name: &str, req: RecallRequest) -> Result<RecallResponse, ServiceError>; }
// ServiceConfig gains `pub recall_timeout: Duration` (60 s) and `pub recall_concurrency: usize` (1).
// Route: POST /v1/namespaces/{ns}/collections/{c}/recall  (body RecallRequest; 200 RecallResponse)
```

**Semantics:**
1. One pin for the whole call; every search runs at it.
2. **Sampling.** `num` documents are drawn uniformly without replacement, with a ChaCha RNG seeded by `seed`, from the snapshot's live rows that hold the vector (durable and tail). Fewer such rows than `num` → all of them. None → `InvalidArgument`. The query vector is the sampled document's stored vector.
3. **Each query.** The ANN side is a vector retriever with `k`, `params` and `filter` through the normal path (the hot tier as the request's `Operon-Hot` allows). The exact side is the same retriever with `params.exact = true`, scored by the exact kernel (D79). Recall is `|ANN ∩ exact| / |exact|`, with Task 2's tie rule: an ANN hit whose exact distance equals the k-th exact distance counts. A query whose exact side is empty (the filter matches nothing) is not evaluated. The sampled document is among both results when the filter allows it, as in turbopuffer's endpoint.
4. `avg_recall` and `min_recall` are over the evaluated queries; the two counts are means of the hits each side returned. `hot_used` is the union over the ANN side.
5. `params.exact = true`, `num` or `k` out of range, an unknown or sparse vector field: `InvalidArgument`. Past `recall_timeout`: `Timeout`.
5a. **Admission.** M1 has no authentication and no query semaphore, and one call runs up to 200 searches, so the process runs at most `ServiceConfig.recall_concurrency` (default 1) recall calls at once; another is refused with `ResourceExhausted` (M1.3 Task 15; HTTP 429, `retry_after_ms` 1 000) before it pins. M2's weighted semaphore and roles replace this (D98).
6. **Cross-check** (`bench/recall/endpoint_check.py`, nightly and full tiers): on Task 6's `glove-100-angular` collection with default parameters, call the endpoint with `num = 100`, a fixed seed and `return_samples`; compute the same 100 queries' recall in the harness (its own ANN calls and its NumPy ground truth).
