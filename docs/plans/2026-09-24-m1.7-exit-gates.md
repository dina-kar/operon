# M1.7 — M1 Exit Gates Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans. Execute task by task, test first. Each task lists the interfaces it must produce and the tests that must exist and pass before it is done. Where this plan gives exact values (names, paths, formats, constants), use them verbatim. The code is not pre-written in this plan (M0.3 Ruling 1).

> **Status: Planned** (2026-09-24).

**Goal:** Prove milestone M1 and close it. Ship:
- the conformance runner and the four framework suites of the M1 gate (LangChain and LlamaIndex vector stores, Elasticsearch and Qdrant backends), plus the Qdrant and Elasticsearch Python client suites, run unmodified against Operon's gateways, each measured against a real Elasticsearch or Qdrant oracle;
- the BEIR harness: nDCG@10 per dataset within 1 point of Elasticsearch BM25;
- the recall harness: Recall@10 within 1% of Qdrant at equal hot-tier latency, unfiltered and filtered;
- the hot on/off differential harness at scale, and the CI mode that disables the hot tier at random per request;
- object-store request counts per query in every benchmark result, with a regression check;
- the CI tiers (every PR, nightly, pre-release) and the M1 exit report.

**Architecture:**
- `operon-store::CountingStore` wraps the server's one object store and counts requests per operation and per path class, as S3 would bill them. The `operon` binary exposes the counters and per-gateway request counters at `GET /v1/admin/metrics`, and gains `--hot-chaos <p>`, a tower layer that adds `Operon-Hot: off` to a seeded random fraction of incoming requests.
- `bench/` is one Python project (uv, Python 3.12), package `operon_bench`: server and oracle lifecycle, datasets, result files, metrics and gate rules. It holds three harnesses: `bench/beir/`, `bench/recall/` and `bench/differential/`. Results are JSON files under `bench/results/`, committed only from the reference machine.
- `conformance/` is a second Python project that depends on `operon_bench`. `suites.toml` pins each upstream suite (repository, tag, commit, install command, test command, environment). `run.py` clones the suite at its commit into `target/conformance/`, installs it with the suite's own lock file, runs its own pytest command with only the environment pointing at Operon (or at the oracle), and writes a report with one outcome per test. `expected/<suite>.json` is the committed outcome of the same run against the real oracle; the gate compares the two.
- Elasticsearch and Qdrant run only as external oracles, in containers (podman or docker, `--network host`), pinned by digest (overview R14). No Elastic code, spec or test resource enters the repository.
- CI tiers (Task 8): **smoke** on every PR (`ci.yml` jobs `python` and `gates-smoke`: debug build, minutes); **nightly** (`gates.yml`: release build, all six suites plain and under hot chaos, the BEIR nightly subset, recall on `glove-100-angular`, the differential at medium scale, the cost check); **full** (`gates.yml` by `workflow_dispatch`, and by hand on the reference machine before a release and for the exit report: everything).

**Tech Stack:** Rust 1.97.1; only `operon-store` and `operon` change, with no new dependency (`rand_chacha` 0.9 and `tower` are already in the workspace). Python 3.12 managed by uv 0.12.13; exact pins in `bench/pyproject.toml`: `numpy` 2.5.3, `h5py` 3.16.0, `pyarrow` 25.0.1, `httpx` 0.28.1, `jsonschema` 4.26.0, `pytrec-eval-terrier` 0.5.10, `elasticsearch` 8.19.3, `qdrant-client` 1.19.1; dev `pytest` 9.1.1, `ruff` 0.16.8. Each upstream suite brings its own pinned environment (Task 3, Task 4). Oracles: `docker.io/library/elasticsearch:8.19.22` and `docker.io/qdrant/qdrant:v1.19.1`, pinned by digest in `bench/oracles.toml`, run with podman 6.1 (the reference machine) or docker (CI).

## Global Constraints

Same as the M1 overview §8, plus:
- **Unmodified means unmodified** (Ruling 1). An upstream framework suite runs from its release's files at a pinned commit, installed from its own lock file (or, where upstream has none, a lock we commit under `conformance/locks/`), with its own test command. Operon may only change the environment (variables, a running server, the ports it listens on) and append `--junitxml <path> -rA -p no:cacheprovider` (plus `-p no:xdist` for `langchain-qdrant`, Ruling 4). No conftest, plugin, patch, monkeypatch, `-k` or `--deselect` of ours in a gated run. Exclusions are by stated feature rule only (Ruling 3): excluded tests still run and are reported.
- **Every gate is non-vacuous.** A gate run fails when: a server-backed suite produced no gateway request; a harness ran zero queries; the hot-on side of a differential never used a hot structure; or an oracle run is missing. A skipped or empty run is never a pass.
- **Measure the oracle, do not quote it.** Every reference number and every expected test outcome comes from a run of the same harness against the real server, recorded with its image digest. Published numbers (BEIR paper, ann-benchmarks site) are only sanity checks.
- **Scratch space:** datasets live in `target/bench-data/`, upstream clones and their environments in `target/conformance/`, run outputs in `target/gates/`. Never `/tmp`: it is a small tmpfs on the reference machine.
- **Python:** Python 3.12, uv only (`uv sync --locked`, `uv run`). `bench/uv.lock` and `conformance/uv.lock` are committed. Python code passes `ruff check` and `ruff format --check` (ruff 0.16.8) and `pytest` in CI.
- **Results:** a committed result file is written only by the full tier on the reference machine and committed by a human in a PR; CI never commits.
- Commit areas used: `store`, `operon`, `bench`, `conformance`, `ci`, `docs`.

## Review Focus

1. **A gate that passes because nothing ran.** The llama-index and elasticsearch-py suites skip every test when no server answers; a hot-off switch that switches nothing makes the differential trivially identical; a harness with zero queries passes every "all queries" rule. Tests: Task 3 `a_forbidden_skip_message_fails_the_gate`, `zero_gateway_requests_fail_the_gate`, `a_new_or_missing_test_is_drift`; Task 7 `a_hot_used_header_on_a_hot_off_response_fails_the_run` and Semantics 6; Task 6 Semantics 4 (≥ 99% `hnsw`); Task 1 `hot_chaos_injects_the_header_at_the_configured_rate`.
2. **Local-mode tests counted as server passes.** Qdrant `:memory:` and `path=` variants pass regardless of Operon, and dense test ids can contain the word "sparse". Tests: Task 3 `server_and_local_tests_are_classified_by_params`, `a_dense_id_containing_sparse_in_a_vector_name_is_not_excluded`, `node_ids_are_reconstructed_from_junit`.
3. **Latency comparisons skewed by the machine rather than the engine**: a hybrid CPU (performance vs efficiency cores), rootless container networking, frequency drift, the two engines measured minutes apart. Tests and rules: Task 2 Semantics 2–3 (`--network host`, CPU sets) and `an_image_runs_by_digest`; Task 6 `a_noisy_qdrant_rerun_makes_the_run_invalid`, `the_gate_fails_when_operon_cannot_reach_qdrants_latency`, `too_few_points_in_range_make_the_run_invalid`.
4. **Ties, float noise and identical ids in the metrics.** Tied neighbours at the k-th distance, scores that differ in the last bit, arguana queries whose own text is in the corpus, queries with no hits. Tests: Task 2 `recall_counts_ties_at_the_kth_distance`, `int_and_float_differ`; Task 7 `volatile_fields_are_ignored_and_nothing_else`, `a_non_exact_score_is_reported`; Task 5 `identical_ids_are_ignored`, `a_query_without_hits_drops_out_of_the_mean`, `ndcg_matches_a_hand_computed_value`.
5. **Hot structures older than the data.** After upserts, deletes and partial updates, the HNSW artifact and the pinned splits still reflect the previous manifest while the tail and delete bitmaps move on; identity must hold in that window, not only after a rebuild. Tests: Task 7 phases `tail`, `applied`, `rebuilt` and `the_oracle_model_applies_mutations`; Task 5 Semantics 6 (nDCG identical across cold, warm and hot phases).

**Semantics:**
1. **Counting rules (they model what S3 bills, whatever the backend):**
   - `get_opts` with `options.head == true` → `head += 1`; otherwise `get += 1` and `get_bytes +=` the length of the returned range (for a whole-object GET, the object size from `GetResult.meta.size`, counted when the call returns, not when the stream is drained).
   - `get_ranges` is **not** overridden: the trait's default coalesces the ranges and calls `self.get_opts` once per coalesced range, which is how the S3 backend issues them, so each coalesced range counts one GET even over `file://`.
   - `put_opts` → `put += 1`, `put_bytes += payload.content_length()`.
   - `put_multipart_opts` → `put += 1` at initiation; the returned upload is wrapped so that each `put_part` adds `put += 1` and its bytes, and `complete` adds `put += 1`; `abort` adds `delete += 1`.
   - `list` and `list_with_offset` → `list += 1` when the stream is created, plus `list += 1` for every further 1000 items yielded (S3 pages hold 1000 keys); `list_with_delimiter` → `list += 1`.
   - `delete_stream` → `delete += 1` per path yielded by the input stream.
   - `copy_opts` → `copy += 1`; `rename_opts` is not overridden (default = copy + delete).
   - Every request is counted whether it succeeds or fails, under the `PathClass` of its path (for `copy`, of the destination).
2. **`PathClass::of(path)`**, on the path relative to the store root (after any bucket prefix), first match wins: `meta/` → `Meta`; `wal/` → `Wal`; `ns/*/streams/` → `Segment`; `ns/*/links/` → `Link`; `ns/*/collections/*/lance/` → `Lance`; `ns/*/collections/*/text/splits/` → `Split`; `ns/*/collections/*/text/deletes/` → `SplitDeletes`; `ns/*/collections/*/manifests/` → `Manifest`; `ns/*/collections/*/hot/` → `Hot`; `ns/*/pk/` → `Pk`; anything else → `Other` (`*` is exactly one path segment).
3. **Server wiring.** `Server::start` builds the store as today, then replaces it with `Store::new(Arc::new(CountingStore::new(store.inner().clone(), counters.clone())))` before anything else uses it, so the metastore, the log, the cache, Lance, SlateDB and the hot tier all see the counting wrapper (Task 0 A10). Counting is always on (a handful of relaxed atomic adds per request).
4. **Gateway request counters.** Every listener's service stack gets a counting layer (outermost, after the chaos layer) that increments `requests` for its `Surface` and, when the response carries `Operon-Hot-Used` (gRPC trailer `operon-hot-used`) with a value other than `none`, `hot_used_responses`; `hot_off_requests` counts requests that carry `Operon-Hot: off` after the chaos layer ran.
5. **Hot chaos.** For request number `n` on a surface (a per-surface `AtomicU64` starting at 0), draw `u = ChaCha8Rng::seed_from_u64(seed ^ ((surface as u64) << 56) ^ n).random::<f64>()` (`surface as u64` = the variant's index in declaration order); if `u < probability` and the request has no `Operon-Hot` header, insert `Operon-Hot: off` (gRPC: metadata `operon-hot: off`) and increment `chaos_injected`. Requests with an explicit `Operon-Hot` header are left alone. The layer applies to every surface that serves reads (native, ES, Qdrant REST, Qdrant gRPC, Flight SQL (metadata `operon-hot`), MCP). `--hot-chaos` with `--hot=off` is rejected at startup (`ServerError::Config("--hot-chaos needs the hot tier on")`; add the variant if Task 0 finds none).
6. **Metrics route.** `GET /v1/admin/metrics` on the native listener returns 200:
   ```json
   {"store": {"total": RequestCounts, "by_class": {"<path_class>": RequestCounts, …}},
    "gateways": {"<surface>": SurfaceCounts, …},
    "hot_chaos": {"probability": f64, "seed": u64} | null}
   ```
   Classes and surfaces with all-zero counts are omitted. The route is served in `operon dev` and `operon standalone` (no authentication in M1, overview §6.9).

8. **Cost regressions.** `cost_regressions(new, baseline)` compares `store_requests.<phase>.per_query.class_b` and `.class_a` of a new result with the latest committed result of the same gate, dataset and machine, and reports a regression when `new > baseline × 1.10 + 0.05`. 9. **Recall rule** (`recall_at_k`, the ann-benchmarks `knn` rule, so ties at the k-th distance do not penalise either engine): let `t` = `true_dists[k-1] + 1e-3` (distances in the dataset's metric: angular = 1 − cosine, Euclidean = L2); recall = |{i < k : found_dists[i] ≤ t}| / k, where `found_dists` are the **exact** distances of the returned ids, recomputed by the harness from the dataset vectors in float64. The ids in `true_ids` are used only when `true_dists` is absent (then recall = |found[:k] ∩ true_ids[:k]| / k).
10. **Latency matching.** `pareto_frontier` keeps the points not dominated (lower latency and higher recall); `recall_at_latency` interpolates linearly between the two frontier points that bracket the latency, returns the frontier's best recall at or below it when the latency is beyond the slowest point, and `None` when the latency is below the fastest point.
11. **Canonical JSON.** `canonical_json` sorts object keys recursively by code point, keeps array order, renders numbers with Python's shortest round-trip `repr` for floats and plain integers for ints (so `1.0` and `1` differ, as they do on the wire), renders strings with `ensure_ascii=False`, separators `(",", ":")`, and removes every object key whose dotted path (array indices dropped) is in `drop`.

CLI: `uv run --project conformance conformance/run.py --tier smoke|nightly|full [--suite <name>]… --target operon|oracle [--hot-chaos <p>:<seed>] [--bless]`. Exit 0 iff every suite's gate passes.

**Semantics:**
1. **Clone and install.** `clone` fetches exactly `commit` (`git init`, `git fetch --depth 1 <repo> <commit>`, `git checkout FETCH_HEAD`; for `run-llama/llama_index` and `langchain-ai/langchain` a sparse checkout of `subdir` plus the repository root files) into `target/conformance/<suite>/src/` and refuses to continue if `git rev-parse HEAD` differs or a tracked file changed after install (`git diff --quiet HEAD` fails); untracked files (virtual environments, the copied lock) are allowed. Each suite's virtual environment lives inside its clone, created by its own install commands with `UV_PYTHON=3.12`. Clones and environments are reused across runs when the commit matches.
2. **Serial execution.** Every suite runs with one pytest process. `langchain-qdrant`'s `conftest.py::pytest_runtest_teardown` deletes every collection on every location after every test, so xdist workers sharing one server delete each other's data; this breaks against real Qdrant too, and upstream CI never noticed because it only runs `:memory:`. That is the only upstream flag we change (`-n auto` → `-p no:xdist`).
3. **Test identity and classes.** A test id is the junit `classname` (dots to `/`, `.py`) + `::` + `name`, exactly pytest's node id. Before the run, `collect_params` runs `pytest --collect-only -q -p conformance.collect_params` with the suite's own command arguments; the plugin (`collect_params.py`, used **only** in this collect-only pass) writes each item's `callspec.params` as `repr` strings to `target/conformance/<suite>/params.json`. A test is **server-backed** when a `server_params` regex matches one of its params or its function name is in `server_names`; otherwise it is `local` (Qdrant `:memory:` or `path=` mode, pure unit tests). A test is **excluded** when an `excluded_params` regex matches the repr of the named param or its function name contains an `excluded_names` substring. Excluded tests still run (nothing is deselected); their outcomes are reported and ignored by the gate.
4. **Targets.** `--target oracle` runs the suite against the real server: Elasticsearch `docker.io/library/elasticsearch:8.19.22` by digest with `discovery.type=single-node`, `xpack.security.enabled=false` and `xpack.license.self_generated.type=trial` (upstream CI's settings, so the licence-gated tests run), ML left enabled (so the "model not deployed" checks get 404 and skip); Qdrant `docker.io/qdrant/qdrant:v1.19.1` by digest. `--target operon` runs a fresh `operon dev` per suite (release binary unless `--debug`), with `--hot-chaos` when given. Both listen on the same ports, so nothing in the suite's environment differs between the two targets.
5. **Expected files.** `--target oracle --bless` writes `conformance/expected/<suite>.json`: `{"format": "operon-conformance-expected", "version": 1, "suite", "commit", "oracle": {image, digest, version}, "machine", "outcomes": {"<test id>": Outcome}}`. It is committed and re-blessed only when a pin or an oracle image changes.
6. **The gate** (per suite, `kind = "framework"`), with `E` the expected outcome and `O` Operon's:
   - every non-excluded **server-backed** test with `E = passed` must have `O = passed`; `E = xfailed` must have `O ∈ {xfailed, passed}`;
   - `E = skipped` must have `O ∈ {skipped, passed}`, and a skip whose message contains any `forbidden_skip_messages` entry is a violation wherever it appears (the llama suites skip silently when no server answers);
   - `E ∈ {failed, error}` is not allowed in an expected file unless the test is excluded: the runner refuses to bless such a file and names the tests (a test that fails against the real server must be understood and excluded with a reason, not ignored);
   - a test in the Operon run but not in `E`, or in `E` but not collected, is a violation (suite drift: re-bless);
   - local tests must match `E` too (they do not exercise Operon, but a difference means the environments differ);
   - non-vacuity: the suite's server-backed passes are ≥ 1 and the gateway's `requests` counter for the suite's backend (`es`, or `qdrant_rest` + `qdrant_grpc`) grew during the run.
7. **Report** (`target/gates/<run_id>/conformance/<suite>.json`, also wrapped as a Task 2 result file with gate `conformance`, dataset = the suite name):
   ```json
   {"format": "operon-conformance-report", "version": 1, "suite": str, "kind": "framework|client", "backend": "es|qdrant",
    "commit": str, "command": [str], "env": {str: str}, "target": "operon|oracle", "hot_chaos": {"probability": f, "seed": u64} | null,
    "gateway_requests": int, "chaos_injected": int,
    "tests": [{"id": str, "outcome": Outcome, "expected": Outcome | null, "server": bool, "excluded": bool, "duration_s": f, "message": str}],
    "summary": {"server": {"passed": int, "failed": int, "skipped": int, "excluded": int}, "local": {…same…}},
    "gate": {"pass": bool, "violations": [str]}}
   ```

   `message` is the junit failure or skip message, truncated to 2,000 characters.

The same data is readable as a Qdrant collection and a native collection (all three surfaces share the namespace `default` and the collection, overview §6.9), so one collection serves the three surfaces.
2. **Phases** (each ends with `queries_per_phase` generated queries compared as in 4–5):

A mismatch is saved to `target/gates/<run_id>/diff/failures/<phase>-<query id>.json` with the request, both responses and both `Operon-Hot-Used` headers.
5. **Approximate class (overview R12's rule).** For each response (hot on and hot off separately): (a) every hit satisfies the query's filter, evaluated by the harness's own model of the collection (`oracle_model.py`: the documents as written, with the mutations applied); (b) every hit's score equals the exact score of its stored vector in the model (cosine similarity; ES `knn` reports `(1 + cos) / 2`) within `1e-4 × max(1, |exact|)`; (c) over all approximate queries of the phase, recall@10 against the model's exact top-10 (tie-tolerant rule, Task 2 Semantics 9) is computed per tier. The phase passes (c) iff each tier's recall is `≥ R_qdrant − 0.01`, where `R_qdrant` is the recall of the same queries against the Qdrant oracle loaded with the same vectors and payloads (`m` 16, `ef_construct` 128, default search parameters), measured by the harness at the end of the run (for `tail`, `applied` and `rebuilt`, the oracle is loaded with the mutated data).
6. **Non-vacuity.** Hot-off responses must all carry `Operon-Hot-Used: none` (anything else is a switch leak and fails the run). In phases `loaded` and `rebuilt`, hot-on responses must report `splits` for ≥ 90% of text queries and `hnsw` for ≥ 90% of approximate vector queries; otherwise the run fails ("the hot tier was not exercised").
7. **Random disabling in CI (§12 §2 item 5).** Besides this harness, the smoke and nightly tiers run the conformance suites with `operon dev --hot-chaos 0.5 --hot-chaos-seed <CI run number> --hot-pin-all` (A13: every collection is pinned when it is created), so every suite's own assertions run with the hot tier randomly disabled per request; the report records `gateways.*.chaos_injected`, which must be > 0.
8. **Result.** `measurements` records per phase and class: queries, mismatches, approximate recall per tier and Qdrant's, the hot-used fractions; `store_requests` per phase and tier. The gate passes iff there are 0 mismatches and every check in 5–6 holds in every phase.

**Tests** (`bench/tests/test_differential.py`, no server):
- `the_generator_is_deterministic_per_seed`: two runs with seed 42 produce identical query sequences; seed 43 differs.
- `every_generated_query_is_well_formed`: 5,000 queries against a fake `CorpusContext` all have a known `kind`, a valid JSON body and a class.
- `volatile_fields_are_ignored_and_nothing_else`: two ES bodies differing only in `took` compare equal; differing in one hit's `_score` by one ulp compare unequal.
- `the_oracle_model_applies_mutations`: after an upsert, a delete and a patch, filter evaluation and exact scores reflect all three.
- `a_hit_outside_the_filter_is_reported`, `a_non_exact_score_is_reported` (`check_approx` on crafted responses).
- `a_hot_used_header_on_a_hot_off_response_fails_the_run`.
- `replay_reproduces_a_saved_failure_file` (against a fake server that returns the saved bodies).
