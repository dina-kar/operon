# M1.4 — Qdrant API Phase A Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans. Execute task by task, test first. Each task lists the interfaces it must produce and the tests that must exist and pass before it is done. Where this plan gives exact values (names, paths, formats, constants), use them verbatim. The code is not pre-written in this plan (M0.3 Ruling 1).

> **Status: Planned** (2026-09-24).

**Goal:** Ship `operon-qdrant`, a Qdrant-compatible gateway over `CollectionService`. It serves Qdrant's REST API on port 6333 and its gRPC API on port 6334 for the Phase A surface of design §06 §8:
- collections: create, delete, get, list, exists; aliases; named dense vectors and named sparse vectors (`sparse_vectors` with `modifier: idf`, overview A26); all four distance metrics; HNSW and quantization parameters, mapped to the hot-tier configuration (`VectorSpec`); shard, replica, cluster and optimizer settings accepted as no-ops;
- points: upsert, delete by ids and by filter, get and retrieve, scroll, count, set, overwrite, delete and clear payload, update and delete vectors, batch update, with dense and sparse vector values;
- search: the universal `query` API (dense and sparse nearest, prefetch, nested prefetch, RRF and DBSF fusion of dense and sparse prefetches, `params.idf`, filters, `using`, `lookup_from`), `query/batch`, `query/groups`, and the legacy `search`, `search/batch`, `search/groups`, `recommend` (with `average_vector`, `best_score` and `sum_scores`, plus batch and groups), `discover` and `discover/batch`; `with_payload`/`with_vectors` selectors, `score_threshold` and `offset`;
- payload indexes: keyword, integer, float, bool, datetime, uuid and full-text, mapped to `add_fields`;
- snapshots: create and list, backed by manifest versions.

The official Python `qdrant-client` (1.15.1 and 1.19.1) runs against `operon dev` in CI. Every endpoint and parameter that the LangChain and LlamaIndex Qdrant suites use (for the M1.7 gate) is covered by a task with a test.

**Architecture:**
- `operon-qdrant` has three layers:
  - One **protocol-neutral core**, built on a hand-written serde model of Qdrant's REST types (`model::*`).
  - **REST** (axum 0.8) deserializes straight into that model.
  - **gRPC** (tonic 0.14, stubs generated from nine vendored Qdrant v1.19.1 protos) converts protobuf messages into the same model and back (`convert::*`).
- So each operation has one executor, and REST and gRPC cannot drift apart.
- The core compiles each request to the M1.2 contracts: `DocOp` batches for `CollectionService::write`; `SearchRequest` with `Retriever::{Vector, Sparse, Fused, Rescore}` and a `Query` filter for `CollectionService::search`; plus `get`, `scroll`, `count`, `add_fields`, `update_aliases` and `versions`. The gateway never reaches storage (overview §8).
- **Gateway-side logic.** The core itself implements the Qdrant behaviour that has no IR equivalent, using Qdrant's exact formulas (Ruling 10):
  - score conversion and thresholds;
  - cosine normalisation;
  - the `recommend` `best_score`/`sum_scores` strategies, `discover`, `context` and MMR, all scored over IR-produced candidates;
  - grouping;
  - payload selectors, and `set_payload` with `key`.
- **Payload filtering.** Every Qdrant collection carries one catch-all JSON field `payload` over its whole `_source`, so any payload key can be filtered without an index, as in Qdrant (Ruling 5, overview A3). Payload indexes add typed, lenient fields (overview A2) that filters never read, since fields added later are not backfilled (overview A4).
- **Wiring.** The `operon` binary starts both listeners behind the cargo feature `qdrant` (on by default). Each request is served in one namespace: the configured default, or the one named in the `Operon-Namespace` header or the `operon-namespace` gRPC metadata key (overview §6.9). Both listeners are wrapped in M1.2's `HotLayer`, so `Operon-Hot: on|off` (gRPC metadata `operon-hot`) switches the hot tier per request and every response carries `Operon-Hot-Used` (overview A13, A23).

## Global Constraints

Same as the M1 overview §8, plus:
- **Envelopes.** Every REST response uses Qdrant's envelope. A success is `{"result": …, "status": "ok", "time": <seconds f64>}`; the only exception is `GET /`, whose body is unenveloped. An error is `{"status": {"error": "<message>"}, "time": <f64>}`, with the status code given in "Qdrant protocol facts". Every gRPC error is a `tonic::Status` with the code and message given there. No input (malformed JSON, protobuf, ids, vectors or filters) may panic or return a non-Qdrant body.
- **Client compatibility.** Every REST response body must parse under both `qdrant-client` 1.15.1 and 1.19.1. Their pydantic models `VectorParams`, `HnswConfigDiff`, `ScalarQuantizationConfig`, `ProductQuantizationConfig`, `BinaryQuantizationConfig`, `KeywordIndexParams`, `IntegerIndexParams`, `FloatIndexParams`, `BoolIndexParams`, `DatetimeIndexParams`, `UuidIndexParams`, `TextIndexParams`, `SparseVectorParams` and `SparseIndexParams` are `extra="forbid"` (`qc115:qdrant_client/http/models/models.py`). Inside these objects the gateway emits only the fields that 1.15.1 knows (listed in Task 3), and never emits `null`.
- **Allowed calls.** The gateway calls only `CollectionService`. It holds no metastore handle (neither `Arc<dyn MetaStore>`, M1.2a, nor the openraft `MetaClient`), `Store` or `LogWriter`.
- **Vendored protos.** The vendored `.proto` files keep their content byte for byte, except the one import edit in Ruling 2. `NOTICE` lists them under "Third-party attributions" as Apache-2.0 files from qdrant/qdrant v1.19.1, with `qdrant.proto` marked as modified.
- **Divergences.** Every behaviour that deliberately differs from Qdrant is listed in the crate docs (`crates/operon-qdrant/src/lib.rs` module doc, section "Divergences from Qdrant 1.19"), with the ruling that made it.
- **Commit areas:** `qdrant`, `operon`, `ci`, `docs`.

## Review Focus

1. **Point ids in every accepted form.** Covers u64; dashed, simple, braced and URN UUIDs in any case; and the digit string `"123"`. Rules for every gRPC service:
- Each service accepts and sends gzip, like Qdrant (`qdrant:src/tonic/mod.rs:183-217`). `max_decoding_message_size` is `max_request_bytes`.
- Every response carries `time` (seconds, f64).
- Output vectors use the `VectorOutput.vector` oneof (`dense`) with the deprecated `data` field left empty (`qdrant:lib/api/src/conversions/vectors.rs:102-130`). Input accepts both `data` and `dense`.
- Protobuf `Value` to JSON (`json_with_int.proto`): `integer_value` becomes a JSON integer, `double_value` a JSON float, `null_value` becomes `null`, and structs and lists recurse. JSON to protobuf: an integer that fits `i64` becomes `integer_value`; any other number becomes `double_value`.
- `PointId { num }` is `U64`, and `PointId { uuid }` is parsed with `Uuid::parse_str`; a failure is `INVALID_ARGUMENT` `Unable to parse UUID: <s>` (`qdrant:lib/api/src/grpc/conversions.rs:1288-1305`).
- A message's `timeout` field (seconds) and the `grpc-timeout` header both bound the request; the smaller one wins.

**Scoring formulas** (all verified in the Qdrant source; all compute with `f32`):
- **Raw similarity `sim(a, b)`**, used by recommend, discover, context and MMR (`qdrant:lib/segment/src/spaces/simple.rs:36-235`):
  - Cosine and Dot: `Σ aᵢbᵢ`. For Cosine, both vectors are normalized first (Ruling 8).
  - Euclid: `-Σ (aᵢ-bᵢ)²`.
  - Manhattan: `-Σ |aᵢ-bᵢ|`.
- **Output score of distance-scored results:** Cosine and Dot return `sim`; Euclid returns `sqrt(|sim|)`; Manhattan returns `|sim|`. From the IR (larger is better, negated distance): Euclid and Manhattan return `-ir_score`.
- **`average_vector`** (`qdrant:lib/segment/src/vector_storage/query/reco_query.rs:144-252`): `avg(pos)` when there are no negatives, else `avg(pos) + avg(pos) - avg(neg)`, element-wise. Then run a nearest search with that vector, which is normalized for Cosine. Example vectors given by id are the stored (normalized) vectors.
- **`best_score`** (`reco_query.rs:68-92`): let `p = max sim(c, pos)` and `n = max sim(c, neg)`, with `-inf` when a list is empty. The score is `sig(p)` if `p > n`, else `-sig(n)`. Here `sig(x) = 0.5 × (x / (1 + |x|) + 1)` (`qdrant:lib/common/common/src/math.rs:7-18`).
- **`sum_scores`** (`reco_query.rs:119-135`): `Σ sim(c, pos) - Σ sim(c, neg)`.
- **`discover`** (`qdrant:lib/segment/src/vector_storage/query/discover_query.rs:20-73`): `rank + sig(sim(c, target))`, where `rank = Σ_pairs cmp(sim(c, pos), sim(c, neg))` and `cmp` is Greater = 1, Equal = 0, Less = -1. With no context pairs, discover behaves as `nearest(target)`.
- **`context`** (`context_query.rs:53-117`): `Σ_pairs (x / (1 + |x|))` with `x = min(sim(c, pos) - sim(c, neg) - f32::EPSILON, 0)`.
- **These four scores are larger-is-better** and are not post-processed (`qdrant:lib/shard/src/query/mod.rs:157-169`).
- **Example ids.** Point ids used as examples (recommend, discover, context, and nearest by id) are excluded from the results when they are in the searched collection. They are not excluded when they come from `lookup_from` (`qdrant:lib/collection/src/operations/universal_query/collection_query.rs:523-532,701-705`).
- **MMR** (`qdrant:lib/shard/src/query/mmr/mod.rs`, `collection_query.rs:473-483`):
  - `λ = 1 - diversity` (default `diversity = 0.5`); `candidates_limit` defaults to `limit`.
  - Relevance is `sim(query, c)`, and the pairwise term is `sim(cᵢ, cⱼ)`.
  - First pick the candidate with the highest relevance. Then repeatedly pick `argmax λ·rel - (1-λ)·max_{s ∈ selected} sim(c, s)`.
  - Returned points keep their nearest-search output scores.
- **RRF** (Qdrant form): `score(p) = Σ_lists 1/(pos + k)` with `pos` 0-based and default `k = 2`.
- **DBSF:** for each list, compute its mean `μ` and sample standard deviation `σ` (n - 1) with Welford's method. Map each score `s` to `(s - (μ - 3σ)) / (6σ)`. A list of one point scores 0.5, and a list whose `μ - 3σ == μ + 3σ` scores 0.5 everywhere. Then sum per point and sort descending.

**Sparse vectors** (overview A26–A29; Ruling 21):
- **Config.** `CreateCollection.sparse_vectors: {name: SparseVectorParams}` with `SparseVectorParams { index?: SparseIndexParams { full_scan_threshold?, on_disk?, memory?, datatype? }, modifier?: "none" | "idf" }` (`qdrant:lib/collection/src/operations/types.rs:1503-1571`; `Modifier`, `qdrant:lib/segment/src/data_types/modifier.rs:13-17`). `CollectionParams.sparse_vectors` is an `Option<BTreeMap>` serialized only when `Some` (`qdrant:lib/collection/src/config.rs:146-149`). In qdrant-client 1.15.1 both `SparseVectorParams {index, modifier}` and `SparseIndexParams {full_scan_threshold, on_disk, datatype}` are `extra="forbid"` (`qc115:qdrant_client/http/models/models.py:2838-2921`); `memory` is 1.19-only. gRPC: `CreateCollection.sparse_vectors_config = 16: SparseVectorConfig { map<string, SparseVectorParams> }`, `SparseVectorParams { optional SparseIndexConfig index = 1; optional Modifier modifier = 2 }`, `enum Modifier { None = 0; Idf = 1 }` (`qdrant:lib/api/src/grpc/proto/collections.proto:97-112, 261-274, 566, 638`; `CollectionParams.sparse_vectors_config = 10` on output).
- **What the suites send.** LangChain creates `sparse_vectors_config={name: SparseVectorParams(**sparse_vector_params)}` with `sparse_vector_params = {}` by default, so `{name: {}}`, next to `vectors_config={}` (SPARSE) or one dense vector (HYBRID) (`lc110:libs/partners/qdrant/langchain_qdrant/qdrant.py:906-982`), and checks `get_collection(..).config.params.sparse_vectors` for its sparse name (`:1252-1270`). LlamaIndex sends `SparseVectorParams(index=SparseIndexParams(), modifier=IDF if the FastEmbed model requires IDF else None)` (`li103:llama-index-integrations/vector_stores/llama-index-vector-stores-qdrant/llama_index/vector_stores/qdrant/base.py:810-836`). `qdrant-client`'s congruence tests use `SparseVectorParams()` and `SparseVectorParams(modifier=IDF)` and compare `config.params.sparse_vectors` between local mode and the server (`qc:tests/congruence_tests/test_common.py:42-46`, `test_collections.py:107-153`, `test_sparse_idf_search.py:18-22`).
- **Values.** A point vector is a named map whose values are dense lists or `{"indices": [u32], "values": [f32]}` (`qdrant:lib/api/src/rest/schema.rs:46-111`). Indices must be unique and the lengths equal (`qe:sparse/common/sparse_vector.rs:302-322`); the stored vector is sorted by index (`qe:segment/data_types/named_vectors.rs:322-327`), and a NaN value is refused (`qc:qdrant_client/local/sparse.py:23-31`; `qc:tests/congruence_tests/test_sparse_search.py:323-360` expects an error from the server). Output uses the same shape inside the named map. gRPC: `Vector.sparse = 102` or the deprecated `data` + `indices`; `VectorOutput.sparse = 102`; `VectorInput.sparse = 3`; `SearchPoints.sparse_indices = 15` with the values in `vector` (`qdrant:lib/api/src/grpc/proto/points.proto:56-146, 563`).
- **Search.** A sparse nearest query scores `Σ qᵢ · wᵢ` over shared indices; points sharing no index are not candidates, a stored zero weight is a shared index, and an empty query returns nothing (`qe:sparse/common/sparse_vector.rs:66-90`, `qe:segment/index/sparse_index/sparse_vector_index/read_view/search.rs:258-300`, `qe:sparse/index/search_context.rs:92-143`). With `modifier: idf` each query weight is multiplied by `ln((N − df + 0.5)/(df + 0.5) + 1)` (`qe:segment/data_types/query_context.rs:274-299`), over the points that have a non-empty vector (`qe:segment/index/sparse_index/sparse_vector_index/vector_index_impl.rs:177-190`). `params.idf` is `"global"` or `{"corpus": Filter}` (`qdrant:lib/segment/src/types.rs:703-732`; gRPC `SearchParams.idf = 6: IdfParams { optional Filter corpus = 1 }`, `points.proto:503-531`) and is refused for a vector without the IDF modifier: "search param `idf` requires a sparse vector with the `idf` modifier" (`qe:shard/query/query_context.rs:26-40`). Sparse scores are larger-is-better and thresholded as `score > t` ("sparse always uses DOT", `qc:qdrant_client/local/local_collection.py:806-846`).

**Filter semantics** (`qdrant:lib/segment/src/payload_storage/condition_checker.rs:69-330`):
- **Boolean clauses.** A filter matches when all of the following hold: every `must` condition matches; `should` is empty or any of it matches; `min_should` has at least `min_count` of its conditions matching; and no `must_not` condition matches. Empty lists contribute nothing (`li:` relies on `should: []` matching everything).
- **`FieldCondition` with several sub-conditions** (`match`, `range`, `values_count`, `is_empty`, `is_null`): true when any of them is true.
- **Arrays.** A condition is true for an array value when it is true for any element. Arrays inside arrays are not flattened.
- **`match.value`:**
  - string = string, bool = bool, integer = a number that `as_i64()`s equal. A float `1.0` does not match `1`.
- **`match.any`:** a string list matches strings and an integer list matches integers. `any: []` matches nothing.
- **`match.except`:** a string or integer is true when it is not in the list. A value of another type is true, except `null`, which is false. A missing key is false.
- **`range`:** numbers compared as `f64`. Non-numbers are false.
- **`is_empty`:** true for a missing key, `null` or `[]`.
- **`is_null`:** true for `null`, or an array containing `null`. A missing key is false.
- **`values_count`:** counts the values at the key, with an array counting its elements. A missing key counts 0.
- **`has_id`:** the point id is in the list.
- **Key paths** (`qdrant:lib/segment/src/json_path/parse.rs`): `key(.key)*` with `[]` (every array element) and `[n]`. A plain `a.b` does not descend into arrays in Qdrant (`json_path/mod.rs:319-342`). Operon's JSON field flattens arrays, so `a.b` also matches `{"a": [{"b": …}]}`. This is a documented divergence.

**Grouping** (`qdrant:lib/shard/src/grouping/`):
- **Group keys.** A point joins the group of each string or integer value at `group_by`. Arrays contribute each element. Values of other types are ignored.
- **Requests.** Each request is the base query plus `must_not IsEmpty(group key)`, excluding already aggregated point ids. It returns `groups × group_size` points.
- **Collecting phase.** At most 5 requests. Each also excludes groups that are already full. It stops once there are at least `groups` full best groups, or when a request returns fewer points than asked.
- **Filling phase.** At most 5 requests. Each is restricted to the unsatisfied best groups.
- **Output.** Groups are ordered by their best hit, in the score order. Hits within a group are ordered the same way and truncated to `group_size`.

**Semantics:**
1. **Compile** (the rules of "Filter semantics", into `Query`):
   1. A filter becomes `Bool { filter: must', must_not: must_not', should: [], minimum_should_match: None }`, where `must'` is:
      - each `must` condition;
      - then `Bool { should: should-conditions }` when `should` is non-empty;
      - then `Bool { should: min_should.conditions, minimum_should_match: Some(min_count.to_string()) }` when `min_should` is present.

      A filter whose lists are all empty compiles to `MatchAll`.
   2. `FieldCondition` with `n > 1` sub-conditions becomes `Bool { should: [each] }`. With none, it is `BadRequest("At least one field condition must be specified")`. Let `f = "payload." + normalized(key)`.
   3. The `match` forms:
      - `value` gives `Term { f, Str | I64 | Bool }`.
      - `any` gives `Terms { f, … }`; an empty list gives `MatchNone`.
      - `except` gives `Bool { filter: [Exists(f)], must_not: [Terms(f, list)] }`; an empty list gives `Exists(f)`.
      - `prefix` gives `Prefix { f, prefix }`.
      - `text` gives `Match { field: f, text, operator: And, minimum_should_match: None, fuzziness: None, analyzer: None }`, and `text_any` the same with `operator: Or`. `phrase` gives `MatchPhrase { f, text, slop: 0 }`. These use the `payload` field's `standard`-analyzed companion whether or not a `text` index exists (Ruling 6, S11).
   4. `range`:
      - Numeric bounds give `Range { f, F64 bounds }`.
      - Datetime bounds are parsed with Qdrant's formats (`qdrant:lib/segment/src/types.rs:114-150`) into `FieldValue::Date(µs UTC)` and give `Range { f, … }`, which M1.2 compiles to the date companion of the `payload` field (Ruling 6, S11); no `datetime` index is needed.
      - An unparseable datetime is `BadRequest("Unable to parse datetime <s>")`.
   5. The remaining conditions:
      - `values_count` gives `ValuesCount { f, … }`.
      - `is_empty: true` and `is_empty: {key}` give `IsEmpty(f)`; `is_empty: false` gives `Bool { must_not: [IsEmpty(f)], filter: [MatchAll] }`. `is_null` works the same way with `IsNull`.
      - `has_id` gives `Ids(parsed ids)`.
      - A nested `Filter` recurses.
      - `geo_*`, `has_vector`, `nested` and `slice` are `Unsupported(<name> condition)` (Ruling 15).
2. The reference evaluator implements the same semantics directly over the payload, including Operon's array flattening for `a.b` (the documented divergence). It returns `Unsupported`/`BadRequest` exactly where `compile_filter` does. Text conditions evaluate over the `standard` analyzer's tokens (`operon_text::tokenizer_manager()`); datetime ranges compare the string leaves that M1.1's `parse_date` accepts, and skip the others (the Ruling 6 divergence).
3. **Payload index** (`PUT /collections/{c}/index`, gRPC `CreateFieldIndex`; body `{field_name, field_schema}`):
   1. A missing `field_schema` is `BadRequest("field_schema is required")`.
   2. Map the type:
      - `keyword` → `Keyword`, `integer` → `I64`, `float` → `F64`, `bool` → `Bool`, `datetime` → `Date`, `uuid` → `Uuid`. Each has `indexed: true, fast: true, ignore_malformed: true`.
      - `text` → `Text { analyzer: "standard", positions: phrase_matching.unwrap_or(false) }` with `fast: false`, for tokenizer `word` (the default) with `lowercase` unset or true: the configuration whose matching the `payload` companion reproduces (Ruling 6). Any other tokenizer or `lowercase: false`, and any of `min_token_len`, `max_token_len`, `stopwords`, `stemmer` or `ascii_folding: true`, is `Unsupported("text index option <o>")`.
      - `geo` → `Unsupported("geo index")`.
   3. `name = "payload_index." + normalized(key)` and `source_path = normalized(key)`.
   4. If a field with that name exists with an equal `kind`, respond `completed` without calling `add_fields`. A different `kind` is `Unsupported("changing payload index type")`. Otherwise call `add_fields(ns, c, vec![field], vec![])`, then respond `UpdateResult { status: completed if wait else acknowledged }`.
   5. `DELETE /collections/{c}/index/{field}` is 501.

Indices are sorted; zero weights are kept.
     - An empty named map `{}` means the point has no vectors.
     - Each vector goes through `check_vector`: an unknown name is `BadRequest("Not existing vector name error: <n>")`, a wrong dimension is `BadRequest("Vector dimension error: expected dim: <d>, got <n>")`, and a non-finite value is `BadRequest("Vector contains NaN or infinite values")`. Cosine vectors are then normalized.
   - A `null` payload becomes `{}`.
   - Each point becomes one `DocOp::Upsert(Document { pk, source: payload, vectors, sparse_vectors })`.
3. **Delete** by ids gives one `DocOp::Delete` per id. By filter, the ids are resolved as in Ruling 13.
4. **Payload.**
   - Setting both `points` and `filter`, or neither, is `BadRequest("Either points or filter must be provided")`.
   - `set_payload` without `key` gives `Patch { mode: MergeTop, source: payload, delete_keys: [], vectors: {}, upsert: None }` per id.
   - `set_payload` with `key`, and `overwrite_payload` with `key`, read the docs and apply `value_set` (for overwrite, the object at the path is replaced by `payload`). Each then gives `Patch { mode: Replace, source: new }` (Ruling 12).
   - `overwrite_payload` without `key` gives `Patch { mode: Replace, source: payload }`.
   - `delete_payload`: when every key is a plain dotted path, it gives `Patch { mode: MergeTop, source: {}, delete_keys: normalized keys }`. Otherwise it is a read-modify-write with `value_remove`, then `Replace`.
   - `clear_payload` gives `Patch { mode: Replace, source: {} }`.
5. **Vectors.**
   - `update_vectors` gives `Patch { mode: MergeTop, source: {}, vectors: {name: Some(v)}, sparse_vectors: {name: Some(s)} }`, with each vector checked as in step 2. `update_filter` is 501.
   - `delete_vectors` gives `Patch { vectors: {dense name: None}, sparse_vectors: {sparse name: None} }` for each listed name. An unknown name is `BadRequest`.
6. **Existence.** Ops addressed by id that Qdrant rejects for a missing point record `must_exist`: set/overwrite/delete/clear payload by ids, `update_vectors`, and `delete_vectors` by ids. Every `write` call uses `WriteOptions { report_existence: !must_exist.is_empty(), atomic: true, ..Default::default() }`: a Qdrant write request is all or nothing (M1.2 Ruling 16), and `atomic` makes the service validate every op before appending any. If any `results[i].existed() == Some(false)` for a `must_exist` op, the response is `PointsNotFound(<first missing id>)`, after the whole batch has been written. An `OpResult::Rejected(e)` (a writer-side rejection after a racing schema change) fails the response with `GatewayError::Service(e)` for the first such op. Ops resolved from a filter never record `must_exist`.
7. **Execute.**
   - The ops of all operations are concatenated in order, and one `write` call is made when the total is at most `filter_write_chunk` or the batch has no filter-resolved ops. Otherwise the ops are chunked (Ruling 13).
   - Result: `UpdateResult { operation_id: Some(max offset in token), status: Completed if wait else Acknowledged }`. `/points/batch` returns one `UpdateResult` per operation, all equal. The REST response carries the token header, and gRPC carries the metadata.
8. **gRPC.** `UpsertPoints`, `DeletePoints`, `SetPayloadPoints`, `DeletePayloadPoints`, `ClearPayloadPoints`, `UpdatePointVectors`, `DeletePointVectors` and `UpdateBatchPoints` are converted into the same model. `wait` defaults to `false`. `PointsOperationResponse { result: UpdateResult { operation_id, status: Completed(2) | Acknowledged(1) }, time }`.

**Semantics:**
1. **Examples.** `resolve_examples` gathers every `VectorInput::Id` in the request (root and prefetches, including recommend, discover and context inputs, and nearest by id). Ids are grouped by `(lookup_from.collection or this collection, lookup_from.vector or using)`, and each group is one `get(…, Projection { source: None, vectors: [name] })`. A missing id is `PointsNotFound(id)`. A missing vector on a found point is `BadRequest("Vector <name> is not found for point <id>")`. `exclude` = the ids that come from this collection.
2. **Compile** (`compile_query`). Let `using = req.using.unwrap_or("")`, which must name a schema vector, dense or sparse (else `BadRequest("Not existing vector name error: <using>")`). `limit` defaults to 10 and `offset` to 0. `k_root = offset + limit`.

   - **Root `None`:** with no prefetch, `retrievers: []`, `kind = Filter` (score 0.0). With exactly one prefetch, the compiled prefetch is the single retriever and `kind` is inherited from it. With several, `BadRequest("A query is required when there are several prefetches")`.

   2. Drop hits whose PK is in `exclude`.
   3. `score = to_qdrant_score(...)`.

   6. Skip `offset` and take `limit`.
   7. Render the payload and vectors.
4. **Batch.** `query/batch` (gRPC `QueryBatch`) runs its requests in order with the same `ctx` and returns `[{points}]`. One failing request fails the whole batch with that error, as Qdrant does.
5. **gRPC.** `QueryPoints` and `PrefetchQuery`'s `Query` oneof (`nearest`, `recommend`, `discover`, `context`, `order_by`, `fusion`, `sample`, `formula`, `rrf`, `nearest_with_mmr`, `relevance_feedback`) are converted into `QueryInterface`. `VectorInput`'s oneof (`id`, `dense`, `sparse`, `multi_dense`, `document`, `image`, `object`) is converted into `VectorInput` (`sparse` → `VectorInput::Sparse`). `SearchParams.idf` (`IdfParams { corpus }`: set → `Corpus`, unset → `"global"`) is converted into `IdfParams`. **Semantics:**
1. **Recommend.** The default strategy is `average_vector`.
   - `average_vector` compiles to `QueryPlan::Ir`: nearest(`average_vector(pos, neg)`), normalized for Cosine, with `kind = Distance`.
   - `best_score` and `sum_scores` compile to `QueryPlan::Scored`. `legs` has one Vector retriever per positive example (`k = candidate_k`, `params`, `select.vectors = [using]`, source per the selectors). With no positives, `best_score` uses one leg per negative. `kind = Custom`.
   - At least one positive, or for `best_score` at least one negative, is required: `BadRequest("No positive examples given")`.
2. **Discover** with a target and at least one pair is `Scored` with legs for the target and each pair's positive. With no pairs it compiles as nearest(target) (`kind = Distance`). **Context** (or legacy discover without a target) is `Scored` with legs for each pair's positive. A context with no pairs is `BadRequest("Context query requires at least one pair")`.
3. **Running a `Scored` plan:**
   1. Run the legs in order. The first uses `ctx.consistency`; the others use `AtLeast(first.read_token)`.
   2. Union the hits by PK, keeping the first vector and source.
   3. Drop `exclude` ids.
   4. Score every candidate with the scorer over its `using` vector, with example vectors normalized for Cosine.
   5. Sort by score descending, then PK ascending.
   6. Apply the threshold (distance order, Ruling 7), skip `offset` and take `limit`.
4. **MMR** (`nearest` with `mmr`):
   1. Candidates: one IR nearest search with `k = candidates_limit.unwrap_or(limit)`, capped at `max_candidates`, with `select.vectors = [using]`.
   2. Drop `exclude` ids, then apply the threshold to the candidates.
   3. Run `mmr_select` with `λ = 1 - diversity.unwrap_or(0.5)`. `diversity` outside `[0, 1]` is `BadRequest`.
   4. Take `offset + limit` picks, skip `offset`, and output each pick with its nearest-search Qdrant score, in pick order.
5. **Legacy routes.** Each is converted with the `From` impls into a `QueryRequest`, and results are the bare list `[ScoredPoint]`, or a list of lists for batches.
   - `search`: `vector: Plain(v)` means `using = ""`, `Named { name, vector }` means `using = name`, and `Sparse { name, vector }` means `using = name` with a sparse `nearest` (Task 7's sparse compile).
   - `recommend`, `discover` and their batches with a sparse `using` are `Unsupported("sparse <kind>")` (Ruling 21).
   - `recommend` maps to `query: Recommend { positive, negative, strategy }` with `using` and `lookup_from`.
   - `discover` maps to `query: Discover { target, context }`, or `query: Context { context }` when `target` is `None`.
   - `with_payload` and `with_vector` default to `false`, and `limit` is required.
6. **gRPC legacy methods.** `SearchPoints` (`vector`, `vector_name`, `filter`, `limit`, `with_payload`, `params`, `score_threshold`, `offset`, `with_vectors`, and `sparse_indices`, which makes `vector` the values of a sparse query on `vector_name`), `SearchBatchPoints`, `RecommendPoints` (`positive`/`negative` ids, `positive_vectors`/`negative_vectors`, `strategy`, `using`, `lookup_from`), `RecommendBatchPoints`, `DiscoverPoints`/`DiscoverBatchPoints` (`target`, `context`) are converted into the same model and answer `SearchResponse`, `SearchBatchResponse`, `RecommendResponse`, `RecommendBatchResponse`, `DiscoverResponse` and `DiscoverBatchResponse`.
