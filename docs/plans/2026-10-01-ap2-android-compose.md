# AP2 — Loams for Android (Jetpack Compose, connect-kotlin) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans. Execute task by task, test first. Each task lists the interfaces it must produce and the tests that must exist and pass before it is done. Where this plan gives exact values (identifiers, channel ids, payload fields), use them verbatim. The code is not pre-written in this plan (M0.3 Ruling 1).

> **Status: Planned** (2026-10-01). **Slot: track AP, after AP0 Task 6 (generation) and in parallel with AP3.** Repository **`ostrium-labs/loams-mobile`**, directory `android/` (§37 §9, D439); until the organisation exists, `dina-kar/loams-mobile`. Branches `ap2-t<N>`, stacked; PRs target `main` of that repository. Tasks 1–9 run against `loams-apps-mock` only. A real server needs the unified auth plan (D111, Q30), AP4 (the server side of AP0's services) and the push gateway; Task 10's store release also needs the Play developer account (Q420).

**Goal:** Ship **Loams for Android**, a native Jetpack Compose app for an operator or approver (§37 §2): pair with a Loams instance by QR or sign in through Custom Tabs, see and decide approvals with a biometric-bound device key, follow operations, jobs and durable runs, and receive end-to-end-sealed push notifications. Every call is Connect-RPC through **connect-kotlin**, generated from the same protos as connect-rust (D128, D438). No web view, no bridge, no KMP (D433).

**Architecture (modules, borrowed from the harness's `core`/`app`/`mock-harness`/`conformance` split, §37 §3.2):**
- **`:core`** (pure Kotlin/JVM, no Android imports): domain models, the pairing payload parser (v1), `DecisionClaims` canonicalization, the watch-stream resume state machine, notification-payload unsealing interface, error-reason mapping. JVM-unit-tested.
- **`:proto`**: Java-lite messages and connect-kotlin clients generated by `buf` from a pinned ref of `ostrium-labs/loams` (`proto/`), with `buf.gen.kotlin.yaml` from AP0 Task 6. Generated sources are not committed; a Gradle task runs `buf generate`.
- **`:data`** (Android library): `ProtocolClient` construction (OkHttp, Connect protocol, binary codec), the `TrustPolicy` (system roots or pinned SPKI per instance), Keystore keys, the token store, Room cache, DataStore settings, repositories exposing `Flow`s.
- **`:push`** (Android library, two flavors): `fcm` (Firebase Messaging) and `unifiedpush` (no Google services); both hand sealed payloads to `:core`'s unsealer (Tink HPKE).
- **`:app`**: Compose UI (Material 3), navigation, ViewModels with `StateFlow` (one ViewModel per screen; no god-object store, a harness lesson), Hilt DI.
- **`:conformance`** (JVM tests): runs AP0's YAML scenarios against a real `loams-apps-mock` process through `:core` + `:proto` + OkHttp on the JVM, with no emulator (connect-kotlin is a JVM library).

**Tech Stack:** Kotlin 2.4 (2.4.20, 2026-09-07), JVM 17, the current stable AGP and Compose BOM (Task 0 pins them), minSdk 29 (Q431), targetSdk the Play requirement at release; **connect-kotlin 0.9.0** (`com.connectrpc:connect-kotlin-okhttp`, `connect-kotlin-google-javalite-ext`; beta, §37 §14 risk 4); OkHttp 5.x (the version connect-kotlin pins, 5.5.0 at 0.9.0); protobuf-javalite 4.x; Hilt; Room; DataStore; WorkManager; `androidx.biometric`; Tink (Apache-2.0) for HPKE; `zxing-android-embedded` (Apache-2.0) for QR scanning in both flavors; Firebase Messaging in the `fcm` flavor only; `org.unifiedpush.android:connector` in the `unifiedpush` flavor. Tests: JUnit 5, Turbine, kotlinx-coroutines-test, Robolectric for ViewModels, Compose UI tests (`androidTest`), Paparazzi or Roborazzi for screenshots (Task 0 picks one).

## Global Constraints

- **Native only.** Compose UI; no `WebView` anywhere except Custom Tabs for sign-in (which is the browser, not a web view).
- **Connect protocol, binary codec, unary and server-streaming only** (AP0). No gRPC trailers needed; HTTP/2 when the server offers it, HTTP/1.1 otherwise.
- **No cleartext.** `network_security_config.xml` sets `cleartextTrafficPermitted="false"` and **does not trust user CAs**; the only exceptions are the emulator's mock host `10.0.2.2` and `127.0.0.1` in the `debug` build type. Pinned instances replace CA validation for that host only (Ruling 3). (The harness allowed cleartext and user CAs app-wide.)
- **`android:allowBackup="false"`** and `dataExtractionRules` exclude everything: tokens, keys and the cache never leave the device. (The harness backed up a plaintext cookie.)
- **No secret in logs, crash reports or screenshots.** `FLAG_SECURE` on the approval and pairing screens. No crash reporter by default (D284's no-telemetry rule; Q433).
- **Commit areas:** `android`, `ci`, `docs`.

## Rulings made while writing this plan

| # | Ruling | Why | Cost if wrong |
|---|---|---|---|
| 1 | **Identifiers:** application id `dev.loams.app`, flavors `fcm` (Play) and `unifiedpush` (F-Droid and de-Googled devices, Q439); notification channels `approvals` (high, bypasses DND only if the user allows), `operations` (default), `jobs` (default), `security` (high), `connection` (low) | One reverse-DNS root; channels let users silence noise without losing approvals | Channel ids cannot be renamed after release without losing user settings |
| 2 | **Two Keystore keys per paired instance**, both EC P-256 (`secp256r1`), StrongBox when `FEATURE_STRONGBOX_KEYSTORE` is present, TEE otherwise: `dpop-<instance>` (no user authentication; signs DPoP proofs for refresh and API calls, so background sync works) and `decide-<instance>` (`setUserAuthenticationRequired(true)`, `setUserAuthenticationParameters(0, AUTH_BIOMETRIC_STRONG or AUTH_DEVICE_CREDENTIAL)`, `setInvalidatedByBiometricEnrollment(true)`; signs `DecisionClaims` only, through `BiometricPrompt` with a `CryptoObject`) | A stolen refresh token cannot approve; a new fingerprint enrolment voids the decision key; the harness's "Keystore AES without user auth for background reconnects" is kept for the first key only | Devices without StrongBox use the TEE; attestation (Q-row) can tell the server which |
| 3 | **Trust:** an instance paired by QR with `spki` set uses a `PinnedTrustManager` that accepts exactly the pinned SPKI set (current and announced next pins, §37 §7.2.3) and checks the hostname against the issuer; instances with `spki: null` use the system trust store **and** still pin the instance key thumbprint (`jkt`) at the application layer (every `GetInstance` must list it in JWKS). A pin mismatch is a hard stop with "this server's identity changed", never a fallback | Self-signed self-hosted servers work; a swapped server is detected even with a public CA; the harness disabled hostname checks for TOFU pairing, which Loams does not | A server that rotates its TLS key without announcing it forces re-pairing; §37 §7.2.3 defines the announcement |
| 4 | **Tokens:** the refresh token is encrypted with an AES-256-GCM Keystore key (no user auth) and stored in DataStore; the access token lives in memory; refresh is DPoP-bound (`dpop-<instance>`) and rotates on use | Same pattern as the harness's `RelayCredentialStore`, plus rotation and binding the harness lacked | None |
| 5 | **Background:** no foreground service for streams. Live updates use `Watch*` streams only while the app is visible; in the background, push wakes the app, and a WorkManager periodic job (15 min minimum, the platform's) syncs the inbox when push is unavailable | Android's background limits; the harness's always-on socket drained batteries and still missed events when killed | Without push (no FCM, no UnifiedPush distributor), approvals arrive only when the periodic job runs, which is best effort: 15 minutes is WorkManager's minimum interval, not a deadline, and Doze or battery optimization can delay it with no fixed upper bound; the UI warns |
| 6 | **Approve from a notification** opens a small activity with the approval card and `BiometricPrompt` directly (action `Review`); there is no background Approve button | A decision needs the decision key, which needs the user present; a one-tap lock-screen approve would bypass that | One extra tap |
| 7 | **No offline decisions.** Decisions are never queued: the Approve button is disabled offline, and a send that fails for network reasons is shown as "not sent" with a retry, reusing the same `idempotency_key` | A decision that lands after expiry or after someone else decided is worse than none; the harness's generation-bound answers taught the same | None |

### Task 2: `:core` — pairing payload, errors, watch resume

**Files:** `android/core/src/main/kotlin/dev/loams/core/{pairing/PairingPayload.kt,errors/Reason.kt,watch/WatchState.kt}` and tests.

**Produces:**

```kotlin
data class PairingPayload(val v: Int, val issuer: HttpUrl, val instanceId: String, val spki: List<String>?, val jkt: String,
                          val code: String, val userCode: String, val exp: Instant)
object PairingPayloads { fun parse(json: String, now: Instant): Result<PairingPayload> }   // refuses v != 1, wrong kind, expired, non-https issuer
enum class Reason { APPROVAL_EXPIRED, APPROVAL_ALREADY_DECIDED, DECISION_PROOF_INVALID, STEP_UP_REQUIRED, PAIRING_EXPIRED, PAIRING_USED, DEVICE_REVOKED, PUSH_TARGET_UNKNOWN, UNKNOWN }
class WatchState<T>(...) { fun onSnapshot(...); fun onUpsert(...); fun onRemove(...); fun onHeartbeat(); fun resumeCursor(): String?; val items: StateFlow<List<T>> }
```

**Semantics:** §37 §7.2.1 (the payload), AP0 Rulings 3 and 6. `WatchState` applies AP0's snapshot/upsert/remove/heartbeat protocol, handles `snapshot_reset`, and declares the stream dead after 45 s without a message (three missed heartbeats); the reconnect backoff is 500 ms ×2 up to 10 s with jitter (the harness's `ConnectionLoop` numbers).

**Tests:** `parse_accepts_v1`; `parse_refuses_v2_and_unknown_kind`; `parse_refuses_expired`; `parse_refuses_http_issuer`; `watch_applies_snapshot_then_changes`; `watch_reset_replaces_items`; `watch_dead_after_three_missed_heartbeats`; `backoff_caps_at_10s`.

**Commit:** `android: add the pairing payload, error reasons and watch state`.

### Task 4: Keys, tokens and pairing

**Files:** `android/data/src/main/kotlin/dev/loams/data/{keys/DeviceKeys.kt,tokens/TokenStore.kt,pairing/Pairing.kt}`, `android/app/.../ui/pair/*`, tests.

**Produces:**

```kotlin
class DeviceKeys(context: Context) { fun dpopKey(instanceId: String): KeyPair; fun decideKey(instanceId: String): KeyPair; fun delete(instanceId: String); fun attestation(instanceId: String): List<ByteArray> }
class Pairing(...) { suspend fun claimFromQr(payload: PairingPayload): Result<PairedInstance>; suspend fun signInWithBrowser(issuer: HttpUrl): Result<PairedInstance> }
```

**Semantics:** Rulings 2 and 4; §37 §7.2.2. QR path: parse, pin, `GetInstance`, check `instance_id` and `jkt`, create both keys, call the token endpoint with `grant_type=urn:loams:params:oauth:grant-type:pairing`, the `code`, `device_name`, `platform=android`, `decision_jwk` (the public JWK of `decide-<instance>`), the key attestation chain, and a DPoP proof. Typed-code path (no QR): the user enters the issuer URL and the 8-digit code, which is redeemed as `user_code` in place of `code` (AP0 Task 2); the app connects with TOFU, shows the server's key fingerprint as 6 words, and tells the user to compare it with the console's display before continuing (the harness's honesty about QR vs typed pairing, §37 §7.2.2). Browser path: Custom Tabs with PKCE at the instance's **Authentik** (the identity provider, owner ruling 2026-10-01) and the app link `https://loams.dev/app/auth/callback` (verified via `assetlinks.json`, Q281), then an RFC 8693 exchange at the Loams gateway with a DPoP proof and the same device registration fields. Device-code path: Authentik's device authorization flow (RFC 8628) when the browser path is unavailable, with the 6-word fingerprint check, exchanged the same way. The typed-code path above becomes a fallback for instances whose Authentik has no device flow (Task 0 checks).

**Tests:** `qr_pairing_round_trip_with_mock`; `typed_pairing_shows_fingerprint_words`; `pairing_code_reuse_is_pairing_used`; `tokens_not_in_logs_or_backup`; `revoked_device_clears_keys_and_tokens` (scenario `device-revoked`).

**Commit:** `android: pair by QR, typed code or browser sign-in`.

### Task 8: Push

**Files:** `android/push/src/{main,fcm,unifiedpush}/**`, `android/core/.../push/Unsealer.kt`, `android/app/.../notify/*`, tests.

**Semantics:** §37 §7.4. On sign-in and on token change, generate (once per instance) an X25519 HPKE key pair in Tink, keep the private key encrypted with a Keystore AES key, and call `RegisterPushTarget` (FCM token or UnifiedPush endpoint, app id, HPKE public key). A message is `{"v":1,"i":"<instance_id>","n":"<notification_id>","s":"<base64 sealed>"}`; the unsealed plaintext is a `loams.notifications.v1.Notification`. Unknown instance or failed unseal shows a generic "New activity in Loams" and syncs the inbox. Approvals post to channel `approvals` with action `Review` (Ruling 6); collapse by `n`. Quiet hours come from the server's preferences, not the device.

**Tests:** `sealed_payload_round_trip` (a fixture sealed by the mock with the device's public key); `fcm_message_has_no_plaintext_fields` (the mock's push log); `unknown_instance_shows_generic`; `approval_notification_has_review_action`; `unifiedpush_flavor_has_no_firebase_classes` (a dependency check).

**Commit:** `android: receive sealed push notifications`.
