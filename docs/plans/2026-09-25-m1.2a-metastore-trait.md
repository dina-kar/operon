# M1.2a — The `MetaStore` Trait Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans. Execute task by task, test first. Each task lists the interfaces it must produce and the tests that must exist and pass before it is done. Where this plan gives exact values (names, paths, signatures, commands), use them verbatim. The code is not pre-written in this plan (M0.3 Ruling 1).

> **Status: Done** (2026-09-26). Written against the as-built code at `2c6b9c6` (M1.1 done). Branch `m1.2a-metastore-trait`, stacked on `m1.1-collection-storage` until that merges; the PR targets `main`. No M1.2 code is written before this plan is merged (D47).

**Goal:** Put the metastore behind a semantic trait before M1.2 adds more metastore callers (D47, architecture review §5). Ship:
- `trait MetaStore` in `operon_common::meta`, covering the whole as-built client surface as named domain operations (no raw KV, no closures over the state machine);
- the shared metastore types (catalog records, fences, leases, pointers, `ApplyError`, `MetaError`, `Consistency`) moved from `operon-meta` into `operon-common`, byte-for-byte the same on disk;
- the openraft `MetaClient` as the first implementation;
- every downstream crate (`operon-worker`, `operon-log`, `operon-link`, `operon-collection`, and the `operon` API layer) on `Arc<dyn MetaStore>`, with `operon-meta` left as a normal dependency only of the composition roots (`operon`, `operon-sim`);
- `operon-meta-conformance`: a backend-agnostic conformance suite, with the linearizability checker, run against the openraft single node and the in-process 3-node cluster now, and against Postgres in M2 (design §12 §2 item 5);
- the M0 and M1.1 gates re-run with no behaviour change.

**Architecture:**
- `operon-common` gains the module `meta`:
  - `types.rs`: the catalog and coordination records moved verbatim from `operon-meta/src/types.rs`, the limits from `operon-meta/src/state/mod.rs`, and the key helpers;
  - `error.rs`: `ApplyError`, `StaleLag`, `log_stale_object` (from `command.rs`) and `MetaError` (from `error.rs`);
  - `store.rs`: `Consistency` (from `node.rs`), `trait MetaStore`, `Tracked<T>`, `MetaChanges`;
  - `views.rs`: owned read models (`PartitionIndex`, `StreamState`, `CollectionHead`, `CollectionRoots`, `LinkHead`) and write requests (`WalCommit`, `SegmentSwap`, `PointerCas`).
- `operon-meta` keeps everything openraft-specific: `Command`, `Reply`, `EntryReply`, `MetaState`, `PartitionState`, `WalCommitRecord`, the codec, `MetaNode`, `MetaConfig`, `Router`, `LogStore`, `StateMachineStore`, `LocalDb`, `Clock`. It re-exports every moved name at its crate root, so `operon_meta::Fence` and friends keep compiling. `impl MetaStore for MetaClient` lives in `operon-meta/src/store.rs`; each trait read is one `MetaClient::read` closure, so it is one consistent snapshot.
- Downstream crates import from `operon_common::meta` and hold `Arc<dyn MetaStore>`. Their tests keep building concrete `MetaNode`s and `MetaClient`s (dev-dependency) and hand them to components through `From<MetaClient> for Arc<dyn MetaStore>`.
- `operon-meta-conformance` (new, `publish = false`): the `linearizability` module moved verbatim from `operon-sim` (which re-exports it), the `Backend` harness trait, the suite, and the `metastore_conformance!` macro. `operon-meta/tests/conformance.rs` instantiates it twice.

**Tech Stack:** Rust 1.97.1, edition 2024. No new third-party dependency:
- `operon-common` gains `async-trait` (MIT OR Apache-2.0) and `tracing` (MIT), both already workspace dependencies. It gains no `tokio`, `openraft`, `postcard` or `futures`.
- `operon-meta-conformance` uses `operon-common`, `tokio`, `async-trait`, `rand`, `rand_chacha` (all in the workspace).

## Global Constraints

Same as the M1 overview §8, plus:
- **No behaviour change.** No `Command`, `Reply`, `ApplyError`, `MetaState` or moved type gains, loses or reorders a field or variant. `SNAPSHOT_FORMAT_VERSION` stays 5. The golden encodings committed in Task 1 are never re-blessed on this branch (`git diff <task-1 commit>..HEAD -- crates/operon-meta/tests/golden/` is empty at the end). `MetaError`'s `Display` texts are unchanged.
- **Existing tests change only mechanically.** A test file that existed at `2c6b9c6` may change only in:
  1. `use` lines and paths (`operon_meta::X` → `operon_common::meta::X`);
  2. converting a concrete `MetaClient` where a signature now wants the trait object (`.into()`, `Arc::new(..)`, `&client` coercing to `&dyn MetaStore`);
  3. reading `MetaState` through the test's own concrete `MetaClient` instead of a component's `meta` field.

  No assertion, expected value, timeout, seed, sleep or test name changes. `crates/operon/tests/fault_matrix.expected.md` is byte-identical.
- **Downstream source never names the openraft types.** Outside `operon-meta`, `operon` (`server.rs` only) and `operon-sim`, no `src/` file names `MetaClient`, `MetaNode`, `MetaState`, `PartitionState`, `Command` or `Reply`, in code or in doc comments (for example `operon-log/src/gc.rs:26` and `writer.rs:47` are reworded to "the metastore clock" and "a metastore write"). The boundary check (Task 10) enforces it through the dependency graph and a grep.
- **The trait is semantic.** No trait method takes a closure, a `Command`, raw bytes, or an untyped key-value pair. Every method's name says what it does in Operon's domain (Ruling 3).
- **One call, one snapshot.** Every trait read returns data from one consistent state. Where the as-built code read several things in one closure and a comment, ruling or test relies on that (GC's clock read with the references, M0.4 I1; trim's pointer and clock; the snapshot's collection, pointer and clock), the trait has one composite method for it (Ruling 7, inventory table).
- Commit areas: `common`, `meta`, `worker`, `log`, `link`, `collection`, `sim`, `operon`, `ci`, `docs`.
- `/tmp` is a small tmpfs. Builds use the repository's `target/`. If a second target directory is needed, it is `CARGO_TARGET_DIR=target/m1.2a-scratch`, deleted after use.

## Rulings made while writing this plan

| # | Ruling | Why | Cost if wrong |
|---|---|---|---|
| 1 | **One `MetaStore` trait**, not domain sub-traits joined by a supertrait. Its methods are grouped by domain (clock and changes; catalog; sequencer and index; leases; pointers; collections; garbage collection) in the trait's docs, in `store.rs`, and in the conformance suite's modules | Every consumer needs several domains (the segmenter uses the index, leases and retired objects; collection GC uses the catalog, pointers, the clock and retired prefixes). One object is passed everywhere, each backend writes one impl block, and no trait upcasting is needed | Splitting later is mechanical: the trait lives in one module and every caller already goes through `dyn MetaStore` |
| 2 | **Dyn-compatibility through `#[async_trait]`** (the `async-trait` crate, MIT OR Apache-2.0, already a workspace dependency used by `Task`, `TaskSource`, `LinkTarget`, `LinkTargetFactory`, `GcRoots`). Futures are `Send`. `MetaStore: Send + Sync + fmt::Debug + 'static`, so `Arc<dyn MetaStore>` works in `Debug`-deriving structs and across spawned tasks | Native `async fn` in traits is not dyn-compatible on Rust 1.97 (verify at execution; if dyn async fn has stabilized, keep `async-trait` for consistency with the other trait objects). Hand-written `Pin<Box<dyn Future>>` returns cost the same boxing with more code | One allocation per metastore call, negligible next to a Raft round trip or a Postgres query |
| 3 | **Semantic, not raw KV (D47).** Reads are named domain queries returning owned records (`stream`, `partition_index`, `collection_head`, `orphan_segments`, …). Writes are the as-built commands, one method each, taking typed arguments or a request struct (`WalCommit`, `SegmentSwap`, `PointerCas`) that mirrors its `Command` without the clock stamp. Pointers are the manifest-pointer domain object (versioned, CAS, fenced, freshness-checked, keys validated and `collection/<id>` checked against the catalog), not a KV store. `MetaClient::read(consistency, closure)` and `MetaClient::write(Command)` stay inherent on the openraft type and are not on the trait | A closure over `MetaState` can only be served by a backend that holds the whole state in memory; a Postgres backend could not run it. Named queries let each backend run one native query or transaction per call (the Lakekeeper model) | ≈50 trait methods. New needs are added as named methods with conformance cases, never as a generic escape hatch |
| 4 | **Cluster administration stays on the concrete openraft types.** Not on the trait: `MetaNode::{start, initialize, id, status, current_leader, wait_for_leader, fatal_error, snapshot, shutdown, watch_applied}`, `MetaConfig`, `Router::{isolate, heal}`, `MetaClient::{new, local, write, write_tracked, read, inject_lost_ack}`, `MetaState::check_invariants`, the codec, and M1.3's learners, membership changes and request forwarding (overview R13). The trait carries only `is_ready()` (the readiness probe) | These are Raft lifecycle and test hooks; a Postgres backend has none of them. Readiness is backend-neutral (openraft: a leader is known; Postgres: the pool is healthy) | None: the composition roots (`operon/src/server.rs`, `operon-sim`) already hold the concrete types |
| 5 | **Which types move to `operon-common`, verbatim:** `Namespace`, `WalClass`, `Retention`, `LinkId`, `TargetRef`, `Link`, `Stream`, `WalChunk`, `EntryKind`, `IndexEntry`, `Lease`, `LeaseGrant`, `Fence`, `Freshness`, `Pointer`, `Collection`, `AliasAction`; the constants `WAL_COMMIT_WINDOW_MS`, `COLLECTION_KIND`, `MAX_COLLECTION_NAME_LEN`, `MAX_NAME_LEN`, `MAX_PARTITIONS`, `MAX_KEY_LEN`, `MAX_LEASE_TTL_MS`, `COLLECTION_POINTER_PREFIX` (now `pub`); the helpers `implicit_name`, `collection_pointer_key`, `collection_prefix`, `collection_pk_prefix`; `Consistency`; `ApplyError` with `stale_lag`, `StaleLag`, `log_stale_object`; `MetaError`. **They stay:** `Command`, `Reply`, `EntryReply`, `MetaState`, `PartitionState`, `WalCommitRecord` (the openraft log's payload and the state machine's internals). `operon-meta` re-exports every moved name from its crate root and its modules use them from `operon-common` | The trait's signatures need the records and the errors; every backend must enforce the same limits and produce the same rejections (the conformance suite asserts them). `Command` is the Raft log payload: moving it would make every backend inherit the Raft command set | None; paths through `operon_meta::` keep working |
| 6 | **The on-disk encoding cannot change, and a golden test proves it.** postcard is not self-describing: it writes struct fields in declaration order and enum variants by index, never type names or module paths. A type moved with identical fields, field order, variant order, serde attributes and derives therefore encodes to identical bytes. Task 1, before anything moves, commits golden encodings of every `Command` variant (Raft log entries), every `Reply` and `ApplyError` variant (M1.3 sends them over the network), and a v5 snapshot of a state built from those commands; later tasks must pass them unchanged. Two type changes are allowed because neither type is serialized: `MetaError::UnexpectedReply` carries the reply's `Debug` text (`String`) instead of a `Reply`, with the same `Display` text, and `MetaError::NotLeader.leader` is spelled `Option<u64>` (`NodeId` is `u64`) | Old Raft logs in redb and old snapshots in object storage must keep decoding | If a derive differs by accident, the golden test fails at once |
| 7 | **Composite reads where atomicity matters.** Each as-built multi-part closure maps to one trait method when the parts must come from one state (inventory table). The GC reads always run `Linearizable` and carry the metastore clock (`retired_expired`, `orphan_wal_objects`, `orphan_segments`, `segment_referenced`, `collection_roots`). Where atomicity never mattered (a `Local` candidate poll, an HTTP description), the call site makes several calls, and the table says so | GC safety depends on the clock and the references coming from one state (M0.4 I1); the trim depends on the pointer and the clock together (M1.1 Ruling 12) | A missed dependency could let GC delete a live object; Review Focus 1 and the GC and simulation gates cover it |
| 8 | **Unknown outcomes stay visible: `Tracked<T>`.** `commit_wal`, `swap_segment` and `cas_pointer` return `Tracked<T> { result, earlier_unknown }`, where `earlier_unknown` says that an earlier attempt within the call ended with an unknown outcome (as-built `write_tracked`). Every other write returns `MetaResult<T>` | The writer's acknowledgement contract (`CommitUnknown`), the segmenter's "delete my segment only after a first-attempt rejection" rule (M0.3 M7, M0.4 E4) and the linearizability histories all depend on it. Any backend that retries has the same ambiguity (a lost Postgres commit acknowledgement) | None; `Tracked::into_result` serves callers that do not care |
| 9 | **The offset watch is `watch_changes() -> MetaChanges`**, armed when it is created: any state change applied after `watch_changes` returns makes `changed()` complete. Spurious wake-ups are allowed; `Err(MetaStopped)` means the metastore stopped and nothing will change any more. `MetaChanges` wraps `Box<dyn ChangeWait>` (an `#[async_trait]` trait), so `operon-common` needs no `tokio`. The openraft implementation wraps `watch_applied()` after `borrow_and_update()`; a Postgres implementation may use `LISTEN/NOTIFY` or a timer | The reader subscribes before planning so a commit between the plan and the wait still wakes it (`reader.rs:151`); the same contract, backend-neutral | One boxed future per wait |
| 10 | **`Consistency` generalizes.** `Linearizable`: reflects every write acknowledged before the call began. `Local`: one consistent state that may be stale; successive `Local` reads through one handle never go backwards. A backend may serve `Local` as `Linearizable` | That is what the openraft implementation already guarantees (the local node's applied state only moves forward); Postgres serves both from the primary | None |
| 11 | **Retries live inside the implementation.** A trait method returns `NotLeader`, `Timeout` or `Unavailable` only after the implementation's own retry budget (`MetaClientConfig::retry_deadline` for openraft). Every write is retry-safe, as each `Command` documents today; the trait docs carry each method's retry behaviour (for example, a retried `create_namespace` reports `NamespaceExists(id)`) | Unchanged as-built behaviour, now part of the contract | None |
| 12 | **Signatures that took `MetaClient`:** struct fields and trait-method parameters become `Arc<dyn MetaStore>`; owned constructor and function parameters become `meta: impl Into<Arc<dyn MetaStore>>`; borrowed parameters become `&dyn MetaStore` when the callee only reads, and `&Arc<dyn MetaStore>` when it keeps a clone. `operon-meta` implements `From<MetaClient>` and `From<&MetaClient>` for `Arc<dyn MetaStore>` (allowed by the orphan rules: `MetaClient` is local) | Tests that pass `meta.clone()` or `&meta` keep compiling, which keeps the "mechanical test edits only" constraint achievable | None |
| 13 | **`operon-sim`, the crash gate and the fault matrix keep testing the openraft implementation, now through the trait.** The simulation still builds concrete meta nodes over a `Router` (isolation, restarts, `check_invariants`, state equality across nodes stay concrete), but every component and the whole workload get `Arc<dyn MetaStore>`: the `CommitWal` and `CasPointer` history operations move from `write_tracked(Command)` to `commit_wal` and `cas_pointer`, so the linearizability checker checks the trait boundary. The crash gate and fault matrix drive the `operon` binary and in-process server, whose wiring hands out `Arc<dyn MetaStore>`; their harnesses and expected tables do not change. Running the simulation and gates on other backends is M2's work | The gates must prove "no behaviour change" on the implementation that ships; routing their traffic through the trait makes them prove the trait path | M2 adds a backend parameter to the simulation |
| 14 | **The conformance suite is a separate crate, `operon-meta-conformance`** (`publish = false`), not a module of `operon-common` behind a feature and not `operon-meta/tests/`. It owns the linearizability checker, moved verbatim from `operon-sim` (`operon-sim` re-exports it as `operon_sim::linearizability`, so `tests/checker.rs` is unchanged). Each backend crate adds it as a dev-dependency and expands `metastore_conformance!(<backend>)`. Cases that need fault injection take it from the backend's optional `Faults` and are skipped (with a printed reason) when a backend has none | Keeps `operon-common` free of `tokio` and test code. A Postgres crate in M2 can use the suite without pulling `operon-sim` (which depends on Lance through `operon-collection`). The checker is std-only, so it moves cleanly | One more crate |
| 15 | **`MetaStore` is implemented only for `MetaClient`**, not for `MetaNode` | Components need leader-following and retries; a bare node has neither | None |

## As built (M1.1, `2c6b9c6`) — facts this plan relies on

- `MetaClient` (`operon-meta/src/client.rs`) has 28 public methods: `new`, `local`, `now_ms`, `watch_applied`, `inject_lost_ack` (test-util), `write`, `write_tracked`, `read`, and one method per command (`create_namespace`, `create_stream`, `create_stream_with_retention`, `create_link`, `commit_wal`, `swap_segment`, `trim_partition`, `set_retention`, `prune_wal_commits`, `forget_objects`, `acquire_lease`, `renew_lease`, `reacquire_lease`, `release_lease`, `cas_pointer`, `cas_pointer_fresh`, `create_collection`, `drop_collection`, `update_collection_schema`, `update_aliases`).
- There is no long-poll or stream-returning method other than `watch_applied() -> tokio::sync::watch::Receiver<u64>`, used by `LogReader::fetch` (`operon-log/src/reader.rs:153`).
- Downstream `src/` reaches metastore state only through `read(consistency, |s: &MetaState| …)` closures (the inventory below) and writes raw `Command`s in three places: `operon-log/src/writer.rs:638` (`CommitWal`), `operon-log/src/segmenter.rs:366` (`SwapSegment`), `operon-sim/src/sim.rs:668,736` (`CommitWal`, `CasPointer`).
- `operon-worker` depends on `operon-meta` too (leases, `TaskContext.meta`, `TaskSource::candidates(&MetaClient)`).
- `operon-common`'s only dependencies are `serde` and `thiserror`.
- The `failpoints` features of `operon-log`, `operon-link` and `operon-collection` forward `operon-meta/failpoints`, but no test of those crates arms a `meta.*` failpoint; only the `operon` crash gate does, through `operon`'s own `failpoints` feature.

## Review Focus

1. **Atomicity lost in the split.** A closure that read the clock with references, or a pointer with the clock, must still be one trait call, or GC can delete a live object and the trim can cut a retained manifest's tail. Tests: Task 4 (`composite_reads_equal_one_state_machine_closure`), Task 6 (the unchanged GC property test and the `gc` tests), Task 10 (crash gate, fault matrix, simulation).
2. **Unknown outcomes.** The writer must still report `CommitUnknown` after an attempt of unknown outcome, the segmenter must still never delete a segment whose swap may have applied, and the linearizability histories must still classify such operations as indeterminate. Tests: Task 4 (`tracked_writes_report_an_earlier_unknown_attempt`), the unchanged `operon-log` writer and segmenter lost-acknowledgement tests (Task 6), Task 9 (the conformance lost-acknowledgement and linearizability cases).
3. **Encoding.** Old Raft log entries and v5 snapshots must decode, and new ones must be byte-identical. Tests: Task 1 golden tests, unchanged through Task 10.
4. **Long-poll wake-ups.** `watch_changes` must be armed before the reader plans, or a fetch at the high watermark can miss a commit and sleep to its deadline. Tests: Task 4 (`watch_changes_is_armed_at_creation`), the unchanged `operon-log` reader long-poll tests, Task 9 (`changes_wake_a_waiter_armed_before_a_write`).
5. **A component that quietly keeps the concrete type.** Tests: Task 10's boundary check (`cargo tree`) and the source grep.
